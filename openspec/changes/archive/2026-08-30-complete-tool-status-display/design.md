## Context

当前工具执行已经有 `tool_queued`、`tool_started`、`tool_progress`、`tool_finished` 和 `tool_result` 事件常量，也有工具结果的超时、取消、清理和输出元数据；但执行器、session 事件翻译和 TUI 之间没有一套完整的生命周期归约。TUI 主要在 `TOOL_CALL` 与 `TOOL_RESULT` 间维护简单的 pending/done/error 状态，导致过程事件没有被投影，进度会污染 running 统计，取消无结果时工具块可能一直处于活动态。

实现必须遵守现有分层：core 只产生运行事实和结构化事件，session 负责 session 事件适配与确认协作，app/tui 负责展示；工具结果已有 `OutputMetadata`/`OutputBuffer` 能力，应复用而不是另造一套截断模型。现有 JSONL 和 `ok`、`cleanup_uncertain` 等历史值需要继续可读取。

## Goals / Non-Goals

**Goals:**

- 为每个工具调用建立可按 `tool_call_id` 归约的生命周期状态快照，完整覆盖排队、执行中、等待确认、终态和清理诊断。
- 让 core/session 的事件字段足以支持 TUI、CLI 和测试直接判断状态，不依赖自然语言文本。
- 让 TUI 工具块实时显示过程、终态、耗时、错误、清理状态和输出完整性，并对并发乱序、重复和缺失结果安全收敛。
- 保持工具执行、确认安全策略、并发上限、模型回填顺序和底部状态栏布局不变。
- 保持旧事件、旧 JSONL 结果和旧状态值的读取兼容。

**Non-Goals:**

- 不重写 ReAct 主循环、工具执行器、超时/取消资源清理算法或确认策略本身。
- 不把 confirmation queue、TUI 组件或持久化实现引入 core。
- 不把每个工具的详细状态全部塞入底部状态栏，也不新增第三方 UI/状态管理依赖。
- 不修改工具结果治理的限制阈值、模型回填文本或 JSONL 的既有字段语义，除非为补充兼容的状态元数据所必需。

## Decisions

### 1. 使用结构化状态快照，而不是由 TUI 推断状态

在 core 的事件/执行契约边界定义稳定的工具状态字段，至少包括 `tool_call_id`、`operation_id`、工具名、生命周期状态、执行状态、`cleanup_status`、耗时、错误码和输出元数据引用。生命周期状态使用 `queued`、`running`、`awaiting_confirmation` 以及 `completed`、`failed`、`rejected`、`timed_out`、`cancelled`、`cleanup_uncertain` 等可序列化值；清理状态和输出完整性独立保留。

选择快照而不是让 TUI 根据“是否有结果”“是否有错误”推断，是因为并发、重复事件和取消无结果都要求状态归约具有确定性。`ok` 与聚合 `cleanup_uncertain` 仅作为旧数据输入的兼容别名，新事件优先使用规范化状态。

### 2. 明确事件产生时机和终态规则

工具调用进入批次时产生排队事件；获得并发槽位、确认许可并真正开始执行时产生开始事件；执行期间产生零个或多个进度事件；结束时产生一次带最终状态和清理诊断的结束事件，随后结果事件只补充结果内容和输出元数据，不改变已经确定的执行终态。

确认请求由 session/app 层广播。需要确认的调用在开始事件前展示 `awaiting_confirmation`；拒绝直接产生 `rejected` 终态，不伪造 running。取消时由 session/app 对仍未收到结果的排队或执行中调用补发可归属的取消收尾，使 UI 不依赖工具结果是否到达。

这种时序保持 core 与确认机制解耦，同时使“排队”和“实际运行”有明确边界；它也允许工具结果真实完成顺序与模型回填顺序继续分离。

### 3. 在 session 适配边界保留旧字段并补齐新字段

事件翻译层继续输出现有 TUI 事件类型，并在 metadata 与类型化快捷字段中传递规范化状态、调用 ID、操作 ID、清理状态、错误码、耗时和输出元数据。旧事件缺少新字段时按事件类型提供安全默认值：`TOOL_CALL` 视为 queued/pending，旧 `TOOL_RESULT` 视为终态，缺失清理或完整性信息视为 unknown。

不要求 JSONL 全量迁移；写入新事件/结果时补充字段，恢复旧数据时做单向兼容映射。这样既能让新 TUI 获得完整事实，也不会破坏已有会话文件。

### 4. TUI 采用按调用 ID 的单向归约器

扩展 TUI 的事件投影，使 `TOOL_CALL`、工具生命周期事件、确认事件、结果事件和 `RUN_CANCELLED` 都更新同一个 `ToolCallBlock`。每个 block 持有一个状态快照和结果缓冲区；事件处理遵循终态不可回退、同类终态幂等、旧进度不能覆盖新状态的规则。若生命周期事件先于工具调用到达，先创建最小占位 block 或暂存事件，随后补齐名称/参数；未知调用 ID 不得更新其它 block。

工具块的摘要行只读取快照，输出区域只读取已有 `OutputBuffer`/输出元数据。执行结论、清理诊断和 `complete/truncated/incomplete/unknown` 结果完整性分别渲染，避免“成功图标”掩盖结果其实被截断。展开、分页和导出继续沿用现有交互，不在事件处理线程做大结果重建。

### 5. 聚合统计按状态迁移计算

运行时快照为每个 `tool_call_id` 记录当前状态或至少记录已计数的终态。`queued → running`、终态迁移各最多计数一次；`TOOL_PROGRESS` 只更新该调用的进度和耗时，不增加 running 计数；超时、取消、拒绝和清理不确定在聚合中保留独立类别，同时可提供失败总数。状态栏继续只显示紧凑聚合信息，工具块承担完整诊断。

选择迁移归约而不是“每个事件累加”，可以同时解决重复 `TOOL_FINISHED`/`TOOL_RESULT`、并发乱序和进度计数膨胀问题。

### 6. 用测试矩阵锁定边界语义

测试按层覆盖：core 验证事件字段与时序，session 验证翻译和旧数据兼容，TUI 验证状态投影与文本/样式快照，集成测试验证取消、超时和并发组合。每个终态都至少覆盖清理已确认和清理不确定（适用时），并额外覆盖成功但输出截断、取消无结果、重复事件和工具 ID 乱序。

## Risks / Trade-offs

- **[状态值兼容复杂度]** `ok` 和 `cleanup_uncertain` 已被现有测试与会话使用 → 保留读取别名和兼容 metadata，规范化只作用于新事件和展示，不做破坏性 JSONL 迁移。
- **[事件到达顺序不稳定]** 并发工具可能先收到结果或终态 → 所有事件按 `tool_call_id` 归约，终态单向收敛，必要时对先到事件建立占位 block。
- **[取消无法确认后代进程]** UI 可能把取消误解为安全结束 → 独立展示 `cleanup_status`，`uncertain/unsupported` 明确保留警告，不将其降级为普通取消或成功。
- **[高频进度造成渲染压力]** 进度事件过多可能影响长会话 → 只更新内存快照，沿用现有帧缓冲/低频刷新和可见区渲染策略，不在每个事件重建大结果。
- **[状态栏信息过载]** 展示更多类别可能导致布局回归 → 状态栏保持聚合和稳定槽位，详细状态仅放入可展开工具块，并增加窄终端断言。

## Migration Plan

1. 先补充 core/session 的状态字段和事件时序，同时保留旧事件名称和结果字段。
2. 接入 TUI 状态归约与工具块展示，再修正聚合计数和取消无结果收尾。
3. 运行旧 JSONL 恢复与全量 TUI/core/session 回归测试，确认旧会话和 headless 订阅方仍可用。
4. 若新展示出现回归，可暂时关闭新增的详细展示映射；事件和兼容读取保留，不需要回滚会话文件。

## Open Questions

无。状态命名、兼容方向、事件时序和展示分层已足以支持任务拆分；具体文案和颜色可在不改变规格语义的前提下由 TUI 实现阶段确定。
