## Purpose

为 Agent 提供可区分的问答、规划和代码修改模式，并在且仅在工作区确实发生变更后建立可取消、可观测且不会虚报完成的验证闭环。

## ADDED Requirements

### Requirement: 会话模式可显式选择

系统 SHALL 支持 `ask`、`plan`、`code` 三种会话模式，并支持 `auto` 作为默认模式。用户 SHALL 能使用 `/ask`、`/plan`、`/code` 对当前消息选择模式，或使用 `/mode <ask|plan|code|auto>` 设置后续消息的粘性模式。

#### Scenario: 单次问答模式

- **WHEN** 用户提交 `/ask 如何运行测试`
- **THEN** 系统以问答模式处理该消息，完成后不改变后续消息的粘性模式

#### Scenario: 粘性代码模式

- **WHEN** 用户提交 `/mode code` 后再提交普通消息
- **THEN** 普通消息以代码模式处理，直到用户再次切换模式或会话结束

#### Scenario: 默认自动模式

- **WHEN** 会话未设置模式且用户提交普通消息
- **THEN** 系统以 `auto` 模式开始，只允许安全的只读探索，并依据实际工作区变更决定是否进入代码验证流程

### Requirement: 模式权限边界

在 `ask` 和 `plan` 模式中，系统 MUST 拒绝写入、编辑、删除或其它会改变工作区的工具调用，并向用户返回可操作的模式切换提示；读取、搜索和解释 SHALL 继续可用。在 `code` 模式中，系统 SHALL 沿用现有工具确认、安全和路径策略。

#### Scenario: 规划模式拒绝写入

- **WHEN** 规划模式中的 Agent 请求修改文件
- **THEN** 文件不发生变化，工具返回拒绝原因和切换到 `/code` 的提示，Agent 可继续给出计划

#### Scenario: 问答模式允许读取

- **WHEN** 问答模式中的 Agent 请求读取或搜索项目文件
- **THEN** 读取成功且不会启动验证或修复流程

### Requirement: 实际变更触发验证

代码任务 SHALL 在执行前记录工作区基线，并在 Agent 回合结束后比较工作区状态。系统 MUST 优先使用 Git 状态和差异识别变更，并可使用工具事件作为补充；只有检测到至少一个实际文件变更时才启动验证。无变更的任务 SHALL 以 `no_changes` 结束且不得执行测试命令。

#### Scenario: 纯问答不触发验证

- **WHEN** 用户询问代码含义且 Agent 只读取文件
- **THEN** 系统返回回答，不执行测试、差异检查或修复回合

#### Scenario: 修改后触发验证

- **WHEN** 代码模式的 Agent 修改了一个工作区文件
- **THEN** 系统进入验证阶段，并使用变更后的工作区执行选定命令

#### Scenario: 外部脚本造成变更

- **WHEN** Agent 调用的命令通过脚本修改文件而没有产生写工具事件
- **THEN** Git/工作区差异仍能检测到变更并触发验证

### Requirement: 验证命令和结果结构化

系统 SHALL 按“用户显式命令 > 项目配置 > 项目文件自动探测”的顺序选择验证命令。验证结果 MUST 包含命令、退出码、成功/失败状态、耗时、是否超时或取消、输出截断标记和有界输出尾部；找不到安全可执行的命令时 SHALL 返回 `unverified`，不得声称任务已完成。

#### Scenario: 显式命令优先

- **WHEN** 用户提供 `pytest tests/test_login.py` 且项目配置另有默认测试命令
- **THEN** 系统只使用用户提供的命令作为本次验证命令

#### Scenario: 自动探测 Python 项目

- **WHEN** 项目包含 `pyproject.toml` 和测试目录且未提供命令
- **THEN** 系统选择项目支持的 Python 测试命令并记录探测来源

#### Scenario: 无可用命令

- **WHEN** 项目没有显式、配置或自动探测出的验证命令
- **THEN** 任务结果为 `unverified`，并说明用户可执行的验证建议

#### Scenario: 验证超时

- **WHEN** 验证命令超过配置的超时时间
- **THEN** 系统终止命令进程树，返回 `timed_out` 结果和有界诊断，不把该任务标记为已验证

### Requirement: 失败修复闭环受控

验证失败时，系统 SHALL 将失败命令、退出码、变更文件、差异摘要和截断错误尾部作为数据传递给修复回合；修复回合 SHALL 使用同一任务上下文，并在每次修复后重新检测变更和验证。默认修复次数 SHALL 为 1，系统 MUST 设置不超过 3 次的硬上限；相同失败指纹重复出现时 SHALL 提前终止并返回 `failed`。

#### Scenario: 一次修复成功

- **WHEN** 首次验证失败且修复回合修改代码后验证通过
- **THEN** 任务结果为 `verified`，并包含验证命令和修复次数

#### Scenario: 达到修复上限

- **WHEN** 验证连续失败直到达到修复上限
- **THEN** 系统停止继续修改，返回 `failed` 和最后一次诊断

#### Scenario: 重复失败提前停止

- **WHEN** 连续两次验证产生相同的命令、退出码、规范化错误和差异指纹
- **THEN** 系统不再启动新的修复回合，返回 `failed`

### Requirement: 任务阶段和取消可观察

系统 SHALL 对外发布 `planning`、`editing`、`verifying`、`repairing`、`completed`、`unverified`、`failed`、`cancelled` 和 `no_changes` 等任务阶段或终态事件。用户取消任务时，系统 MUST 同时取消模型、工具和验证命令，并保证任务最终进入 `cancelled` 或已明确的清理不确定状态。

#### Scenario: 验证阶段可观察

- **WHEN** 任务正在执行测试命令
- **THEN** 订阅者收到验证阶段、命令、当前尝试次数和耗时信息

#### Scenario: 取消整个任务

- **WHEN** 用户在验证或修复阶段发出取消
- **THEN** 当前子进程和后续修复均停止，任务回到可输入状态并显示 `cancelled`

#### Scenario: 正确报告终态

- **WHEN** 任务以成功、失败、无变更、未验证或取消结束
- **THEN** 系统发布唯一终态结果，且不会把普通 Agent 回合结束误报为验证成功
