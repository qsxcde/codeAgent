## Context

当前 `TuiApp` 集中输入、命令、会话、任务、确认、恢复和渲染调度；`components.py` 同时保存富文本基础类型、消息块、布局、状态栏和事件投影。具体 Textual 依赖已被限制在单一 backend，且现有 TUI 规格和测试定义了必须保持的行为。详见 [proposal.md](proposal.md)。

## Goals / Non-Goals

**Goals:**

- 让每个 TUI 模块拥有单一、可描述的职责和单向依赖。
- 保持 `TuiBackend` 端口、事件顺序、渲染输出、命令、会话与退出语义不变。
- 为后续性能优化提供可独立测试的 Transcript、消息块和渲染协调边界。

**Non-Goals:**

- 不改变 Textual 布局、命令集合、模型/工具协议或会话持久化格式。
- 不在本变更中引入新交互、性能算法或新的终端引擎。
- 不强制把每个小函数拆为模块；拆分以稳定职责边界为准。

## Decisions

### 先建立无循环的渲染基础层

新增仅包含 `Span`、`RichLine`、宽度、截断和富文本转换的基础模块。Markdown renderer、消息块、Transcript 和 Textual backend 都依赖该基础层，避免 renderer 反向导入组件模块。

保留临时 re-export 或集中迁移内部引用，直至所有生产与测试导入完成；不暴露新的跨层公共 API。

### 将组件层按“数据块、布局、投影”拆分

- 消息块模块持有用户、助手、工具、错误和取消块的局部状态与渲染。
- Transcript 模块持有 block 顺序、滚动、布局缓存、可见范围与点击映射。
- 状态栏模块持有 footer 与运行态显示。
- TUI model 模块只负责把结构化事件投影为上述组件状态。

这比按视觉文件或按事件类型拆分更稳定：布局优化不会触碰命令状态，新增事件不会耦合 Textual。

### 将 `TuiApp` 拆成协调器而不是新增第二个上帝对象

`TuiApp` 保留 backend 回调注册、初始装配和顶层关闭。交互/命令、会话恢复、对话任务与渲染调度分别抽为小型协调器，通过窄回调或显式依赖访问 manager、model 和 backend。

不引入全局 service locator；依赖仍由 `tui_factory.py` 和 `TuiApp` 构造器显式提供。具体 Textual 类型仍只允许在 Textual backend 模块中出现。

### 以行为测试作为迁移护栏

先为现有关键行为补充纯组件和 fake backend 测试，再逐段迁移代码。每次迁移后执行 TUI 测试和 AST 导入边界测试；最终删除旧实现或仅保留内部兼容 re-export。

## Risks / Trade-offs

- [文件移动造成导入循环] → 先落地基础富文本层，并在每个迁移步骤运行导入边界测试。
- [协调器之间重新形成隐藏共享状态] → 状态只归属 model、manager 或明确的控制器，禁止模块级可变状态。
- [大范围移动掩盖行为回归] → 按组件层、渲染层、会话/任务层分批提交，并使用同一 fake backend 回归场景。
- [过度拆分增加跳转成本] → 只抽取拥有独立状态机或独立依赖方向的职责。

## Migration Plan

1. 提取富文本基础类型并消除 Markdown 循环依赖。
2. 提取消息块、Transcript、状态栏和 model，保持 `components.py` 作为短期兼容入口或一次性迁移全部内部导入。
3. 提取渲染协调，再提取交互、会话恢复和任务协调。
4. 收敛 `TuiApp`、更新工厂装配和导入边界测试。
5. 全量 TUI 行为测试与分层规则通过后删除不再需要的兼容入口；回滚时可恢复到前一迁移提交，不改变持久化数据。
