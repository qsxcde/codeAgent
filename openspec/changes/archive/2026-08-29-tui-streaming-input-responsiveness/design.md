## Context

See `proposal.md` for the motivation and user-visible scope. 当前 TUI 的事件回调、模型归约、`TuiModel.render` 和 Textual widget 更新都运行在同一个 asyncio 事件循环中；`TuiEventBuffer` 已能合并相邻增量，但使用字符串逐次拼接。活动中的 `AssistantBlock` 仍会在缓存失效后重新组合和解析累积正文，`Transcript` 每帧遍历全部块计算布局。实现必须保持 Textual 只能在 UI 线程更新、core/session 公共接口不变，以及 v4-17 提交首帧顺序。

## Goals / Non-Goals

**Goals:**

- 使高频文本/思考增量、长 Markdown 和大工具结果下的输入、Esc、滚动与确认操作保持及时响应。
- 将流式正文处理改为追加式增量计算，避免每个增量重复解析已经稳定的内容。
- 在不丢失或重排事件的前提下控制事件合并、帧提交和缓存占用。
- 保留提交即时回显，并使准备态首帧不依赖完整历史重排。
- 用真实 Textual 事件循环和可重复的性能观测验证用户可感知行为。

**Non-Goals:**

- 不改变 core、session、provider、工具协议、事件格式或持久化格式。
- 不在本变更中重做数万行历史的索引算法；该范围属于 V4-21。
- 不在本变更中建立完整的跨平台性能门禁和发布报告；统一指标归档属于 V4-22。
- 不把 Textual widget 或可变 TUI 模型直接放入后台线程。

## Decisions

### 1. 保持单一 UI 线程，采用协作式帧准备

渲染准备仍由 TUI 事件循环拥有，Textual widget 更新仍在 UI 线程完成。`TuiRenderCoordinator` 增加帧 generation/dirty 状态和可继续执行的帧准备流程：事件归约、可视区域布局和 Markdown 增量处理按有界批次推进，超过当前帧预算时通过下一次 loop turn 继续；只有完整且仍然有效的帧才提交给 backend。新输入、取消或滚动到达时，旧的未提交帧可被 generation 标记淘汰。

选择协作式处理而不是把整个渲染放入线程，是为了避免同时读取和修改 `TuiModel` 的竞态，也避免跨线程调用 Textual。线程方案需要额外的不可变快照、过期帧丢弃和 UI 回调桥接，超出本变更必要范围。

### 2. 增量缓冲使用分段累积并保留结构边界

`TuiEventBuffer` 对同类型增量保存字符串片段列表，而不是每次将完整 payload 重新拼接。达到实现定义的批量上限、帧边界或遇到不同类型事件时，片段一次性合并并归约；单个过大的输入也必须完整保留。工具、确认、错误、取消和终态事件到达时，先刷新所有前置增量，再处理结构事件。

这样可以把事件入口的重复复制从随累计文本增长的成本降为按批次合并，同时保持现有“相邻增量合并、结构事件不跨越”的可观察顺序。

### 3. AssistantBlock 维护追加式 Markdown 状态

活动中的助手块按终端宽度维护稳定前缀、未完成尾部和必要的 Markdown 行状态。新换行或结构闭合后，只解析新增的稳定片段；当前未完成行单独渲染。正文内容使用追加式片段存储，避免每帧为获得完整 body 而反复复制全部历史片段。宽度变化或状态无法安全复用时允许对该宽度做一次完整重建，回合结束时执行一次完整渲染并校正流式中间结果。

最终完整渲染是正确性基线；流式增量渲染只负责及时反馈，必须通过“流式最终帧与完整渲染相等”的测试。每个宽度和活动 revision 的缓存仍受现有有界策略限制。

### 4. 准备态首帧使用轻量路径

保留 v4-17 的“用户消息和准备状态先于 `session.run`”约束，但将 `flush_render_now` 的准备态路径限定为当前已缓存视口、新用户块和状态栏所需内容。它不得为了生成首帧同步 materialize 全部历史或重新解析完整长 Markdown；完整视口重排由后续普通帧继续完成。

输入、滚动和取消回调只修改游标、取消状态或 dirty 标记，不主动执行完整渲染。取消先触发当前 session/task 的 abort，再等待后续终态事件刷新显示。

### 5. 大工具结果保持摘要优先

沿用工具结果默认折叠和结构化 metadata。折叠状态只渲染摘要，不访问完整结果行；展开时只读取当前分页内容。若兼容旧结果缺少 metadata，统计和分页处理也必须在帧准备中保持有界，不能让一次大结果同步占满事件循环。

### 6. 以真实交互链路作为验收入口

在现有纯组件测试之外，增加 Textual `run_test()` 场景：后台 fake session 连续发出高频增量，同时注入输入、Esc、滚轮/PageUp 和确认操作，记录事件顺序、事件循环延迟、最终文本和取消收尾。离线 benchmark 增加控制事件延迟、合并批次和过期帧计数，但不记录 prompt 或用户内容。

性能验收采用受支持基准环境的 p95 ≤50ms、最大 ≤100ms 控制事件延迟，以及单次渲染工作不超过 30fps 的约 33ms 帧预算；测试同时验证没有文本丢失、重复或结构事件重排。时序单测使用注入时钟，避免把所有功能回归绑定到机器瞬时性能。

## Risks / Trade-offs

- **增量 Markdown 与完整 Markdown 不一致** → 回合结束强制完整渲染，并比较流式最终帧与完整渲染结果；遇到不可安全增量处理的结构时退化为当前块重建。
- **协作式帧准备增加状态复杂度** → generation、dirty 和取消路径集中由渲染协调器管理；每个中间状态补充取消、resize、终态测试。
- **极端长历史仍可能有布局扫描成本** → 本变更只保证流式交互不被单个长帧长期占用，并记录长历史数据；完整分段/索引布局移交 V4-21。
- **性能阈值受平台差异影响** → 功能测试使用确定性事件顺序和注入时钟，阈值仅用于受支持基准环境的性能场景，并输出平台信息。
- **准备态轻量帧可能暂时只显示部分已缓存内容** → 强制保证新用户消息和运行状态可见，下一帧补齐正常视口；保留 v4-17 的首帧顺序回归测试。

## Migration Plan

这是纯 TUI 内部实现变更，不涉及持久化迁移、公共 API 版本升级或用户数据转换。先落地增量缓冲和 Markdown 等价性测试，再接入协作式帧准备与 Textual 交互回归；若出现回归，可整体回退 TUI 渲染协调器改动，core/session 数据仍保持兼容。
