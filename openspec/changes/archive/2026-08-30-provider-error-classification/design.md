## Context

当前 `OpenAICompatClient` 和流式传输混入类各自判断是否重试，并在最终失败时重新抛出原始异常。Provider 工厂也没有把自身标识传到传输层。详见 `proposal.md` 的 Why；本设计只处理 AI 传输边界，不把错误模型扩散到核心编排或 UI。

## Goals / Non-Goals

**Goals:**

- 在一次错误分类中统一产生错误类别、可重试性和诊断元数据。
- 让 HTTP、网络和超时异常在非流式与流式路径上拥有一致语义。
- 对响应详情设置长度上限并脱敏，避免 API 密钥、令牌和密码进入错误文本。
- 继续满足已有调用方对 `httpx.HTTPStatusError`、响应对象和错误响应体的兼容预期。

**Non-Goals:**

- 本变更不重新设计退避算法、最大重试次数或用户交互策略。
- 本变更不为每个 Provider 编写独立的 SDK 异常适配器，也不引入新的 HTTP/日志依赖。
- 本变更不把错误分类规则下沉到 `core/`，避免核心领域依赖 AI 基础设施。

## Decisions

### 统一分类器位于 AI 层

新增独立的 `codeagent.ai.errors` 模块，接收原始异常并返回稳定的 `ProviderError`。选择集中分类而不是在每个 Provider 中复制判断，是因为所有内置 Provider 都使用 OpenAI 兼容传输，集中规则可以保证流式和非流式一致；未来非兼容 Provider 也可以复用公共错误模型。

### HTTP 错误保留类型兼容

HTTP 响应分类错误同时继承 `httpx.HTTPStatusError` 和项目错误基类，并保留原始 `request`、`response`。这样既能提供 `kind` 等结构化字段，又不会破坏现有按 HTTP 异常捕获响应体的调用方。网络和超时错误直接使用项目错误基类，避免伪造不存在的 HTTP 响应。

### 分类规则优先使用状态码，参数判断使用受限详情

401/403 归类为认证，429 归类为限流，5xx 归类为服务端，网络/连接归类为网络，超时归类为超时。400/422 仅在受限且脱敏的错误详情中发现“不支持参数”等明确信号时归类为参数不支持，否则归类为无效请求。无法识别的 HTTP 状态归类为 HTTP 错误，其他异常归类为未知错误。

### 只传递稳定元数据

Provider 工厂传入固定 Provider ID；模型 ID来自客户端配置。错误携带状态码、请求 ID和可解析的 `Retry-After` 秒数，但响应详情截断且对常见凭据字段做掩码。分类器不记录日志、不读取环境变量，也不改变现有重试次数。

## Risks / Trade-offs

- [第三方错误体格式不一致] → 同时支持常见 `error.message`、`error` 字符串和原始文本，并对缺失结构使用稳定兜底详情。
- [错误多重继承影响异常行为] → 只对 HTTP 状态错误使用多重继承，保留原始 request/response，并用回归测试锁定兼容性。
- [详情脱敏不可能覆盖所有供应商字段] → 限制详情来源和长度，屏蔽常见敏感键值；不把完整响应体写入日志或错误字段。
- [分类规则误判参数错误] → 只有明确的 unsupported/does not support/unknown parameter 等信号才使用参数不支持类别，其余 4xx 保持无效请求。

## Migration Plan

1. 添加错误模型与分类器，接入 OpenAI 兼容非流式和流式失败路径。
2. 更新内置 Provider 工厂并补充单元、传输和兼容性测试。
3. 运行分层测试、完整测试、Ruff、构建和 OpenSpec 校验后归档变更。

回滚时可恢复传输层的原始抛出路径；该变更不修改持久化格式和外部 API 请求格式。
