## Context

当前状态栏由单个 `RichLine` 按条件顺序追加字段，再整体交给 backend 渲染。运行阶段、任务状态、耗时、当前操作和临时提示都可能在运行期间出现或改变长度；虽然上下文信息会右对齐，但左侧字段仍会被反复截断和重排。

本变更只调整 TUI 的状态栏投影和排版，不改变 core 事件、运行状态值、任务监督器或 `TuiBackend.set_status()` 的接口。相关行为要求见 `openspec/changes/stabilize-tui-status-bar-layout/specs/tui/spec.md`。

## Goals / Non-Goals

**Goals:**

- 将状态栏分成会话信息区、运行状态区和上下文信息区。
- 让区域边界和区域起始位置在状态变化时保持稳定。
- 让计时、token 数和百分比使用受控宽度，避免位数变化导致跳动。
- 使用终端 cell 宽度进行截断和补齐，正确处理中文路径和混合字符。
- 在窄终端中按优先级降级，同时保留运行阶段、当前操作和上下文占用。
- 保持现有状态标签、任务终态、样式标签和单行 backend 契约。

**Non-Goals:**

- 不修改 Agent 运行循环或事件协议。
- 不增加新的运行状态或任务状态。
- 不把状态栏改为多行布局。
- 不在状态栏中新增 session ID、run ID 或完整工具统计。
- 不处理工具块、过程摘要或聊天 transcript 的视觉重构。

## Decisions

### 1. 保留单行 RichLine，内部采用三栏布局

状态栏仍然通过现有 `StatusBar.render(width)` 返回一行 `RichLine`，但不再把字段全部串联追加。渲染流程先计算三栏宽度，再分别渲染并补齐：

```text
会话信息区 | 运行状态区                         | 上下文信息区
模型/cwd   | 任务状态 · 阶段 · 当前操作 · 耗时       | meter/token/percent
```

上下文区保持右边界锚定；会话区和运行区只在各自预算内截断。这样不需要修改 `TuiBackend` 或 Textual 的布局结构，能够以较小范围修复跳动问题。

替代方案：把状态栏拆成三个 Textual 控件。该方案可以由终端引擎处理布局，但会把本应属于纯渲染层的排版策略泄漏到 backend，并增加离线测试和引擎耦合，因此不采用。

### 2. 为每个区域分配稳定宽度预算

状态栏根据终端总宽度计算区域预算：

- 上下文区使用固定的最小/最大预算并始终右对齐；上下文数据未知时仍保留该区域，以占位符或低对比空态表示。
- 会话区使用有限预算，优先保留模型名，其次保留思考强度和工作目录。
- 运行区使用剩余宽度，优先保留阶段，再保留当前操作和耗时。
- 每个区域独立截断和补齐，禁止一个区域的文本长度改变其他区域的起始位置。

具体预算以终端 cell 宽度计算，不使用 Python `len()`。预算常量应集中在状态栏内部，避免散落在各个字段格式化函数中。

替代方案：只在字段之间添加空格。该方案无法处理字段出现/消失、窄终端和右对齐上下文，因此不能稳定解决问题。

### 3. 动态字段使用固定格式

动态字段采用长度可预测的格式：

- 阶段耗时使用至少固定整数位和一位小数，例如 `00.0s`。
- 任务尝试次数使用固定结构，例如 `第 1/3 次`；没有尝试信息时保留运行区空间，不追加新的尾部字段。
- 上下文 token 和百分比使用统一单位与精度，例如 `12.8k / 32k · 40%`。
- 当前操作允许截断，但阶段名称不可被当前操作完全覆盖。

格式化结果先转换为带样式的 spans，再通过 cell 宽度工具截断/填充，避免 CJK 字符导致预算误差。

### 4. 将临时提示纳入运行区，而不是动态追加

`新输出 N`、上下文同步等临时提示放入运行状态区的受控尾部，或者替换当前操作文本；不再作为状态栏最右侧的新字段追加。状态栏只保留有限的短诊断，完整信息继续通过 `/status` 或聊天区反馈。

### 5. 窄终端采用明确的降级优先级

当总宽度不足时，按以下顺序保留内容：

1. 运行阶段。
2. 当前操作的可识别摘要。
3. 上下文占用。
4. 模型名。
5. 思考强度、工作目录、任务命令和次要诊断。

降级只发生在区域内部或在预定义断点隐藏整个次要字段，不允许产生水平溢出、覆盖或重新排列核心区域。现有 resize 防抖机制继续负责窗口变化时的重排；运行状态本身不触发区域结构变化。

### 6. 通过位置断言验证稳定性

测试不仅断言文字存在，还应测量关键区域的 cell 起始位置：在阶段切换、计时位数变化、任务状态出现/结束、长命令截断和上下文数值变化前后，会话区与上下文区的边界必须一致。

现有状态栏语义测试继续保留，新增测试集中在 `tests/ui`，避免引入真实 Textual 终端依赖。

## Risks / Trade-offs

- [风险] 固定预算可能在极窄终端隐藏较多会话信息 → [缓解] 以运行阶段、当前操作和上下文占用为核心优先级，并为 320 cell 左右的宽度增加窄屏断言。
- [风险] 上下文区始终保留占位空间会减少左侧可用宽度 → [缓解] 上下文区只保留最小可读预算，并在极窄模式使用更短的 token 格式或仅保留百分比。
- [风险] 中文、emoji 或组合字符可能使固定宽度计算不准确 → [缓解] 复用已有 `_cell_width`、`_truncate_spans`，并增加 CJK 混合文本测试。
- [风险] 状态栏中同时存在任务状态和 Agent 阶段，内容可能过密 → [缓解] 任务状态归入运行区，验证命令只展示截断摘要，完整诊断继续由任务详情或 `/status` 提供。
- [风险] 用户习惯旧字段顺序 → [缓解] 保留所有原有核心字段和语义，只调整其区域位置与显示优先级。

## Migration Plan

1. 为状态栏增加三栏预算和独立区域渲染辅助逻辑。
2. 将现有 task、mode、runtime、model、effort、cwd 和 context 字段迁移到对应区域。
3. 增加固定格式、CJK cell 宽度、阶段切换和窄终端测试。
4. 运行 focused TUI 测试、编译检查和 OpenSpec 校验。
5. 由用户执行全量测试后再归档变更。

回滚时只需恢复旧的 `StatusBar.render()` 排版实现；没有持久化格式、事件协议或外部 API 迁移。
