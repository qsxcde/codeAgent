## Context

普通文本提交目前由 TUI 协调器先写入待显示用户消息，再通过事件循环创建任务。任务监督器发出的 `planning` 事件和后续会话事件才能驱动常规渲染，因此提交回调返回时并没有可观察的渲染屏障。现有模型已经用待显示用户消息列表处理预回显与 `SESSION_STARTED` 的去重，但尚未覆盖任务在真实会话开始前失败或取消的清理路径。

本设计实现 proposal.md 中的 V4-17 时序约束，依赖现有的 TUI 模型、状态栏、渲染协调器和任务监督器，不改变 core、session、provider 或工具协议。

## Goals / Non-Goals

**Goals:**

- 为普通文本提交建立明确的顺序：用户消息和准备中状态进入 TUI 状态，完成首帧渲染，然后才启动任务和模型/工具初始化。
- 让首帧使用现有 transcript、活动提示和状态栏渲染机制，并保持后续事件驱动渲染不变。
- 让真实 `SESSION_STARTED` 事件与乐观回显幂等合并，同时清理未进入真实会话的失败或取消提交标记。
- 用离线测试记录 backend 帧、状态和会话启动顺序，覆盖成功、初始化失败、取消及重复文本场景。

**Non-Goals:**

- 不向 session 历史或事件总线写入新的合成事件。
- 不调整模型 provider、工具执行、工作区基线或持久化格式。
- 不改变斜杠命令、登录输入、忙碌态草稿和退出流程的既有分派语义。
- 不把所有 TUI 渲染改成同步刷新；同步屏障只用于普通文本提交的首帧。

## Decisions

### 1. 使用 TUI 专属的待提交投影

在 `TuiModel` 中扩展现有待显示用户消息机制，使提交态同时能表达“用户消息已显示”和“任务正在准备”。准备态只属于 TUI 展示状态：可复用状态栏已有的 `planning`/“准备任务”标签及活动提示，不改变 `RuntimeSnapshot`，也不把尚未开始的回合写入会话历史。

提交进入准备态后，TUI 应将任务视为占用输入的运行中操作；真实会话开始或终态事件到达后，由现有事件投影恢复相应状态。若任务在 `SESSION_STARTED` 前失败或取消，只移除待去重标记并保留已显示的用户消息及错误/取消反馈，避免下一次相同文本被误判为重复回显。

备选方案是提前调用 session 的事件入口伪造 `SESSION_STARTED`，但这会污染会话生命周期、运行统计和持久化边界；因此不采用。

### 2. 在启动异步任务前建立同步渲染屏障

普通文本提交在创建会话任务前执行一次受控的立即渲染。该路径应复用 `TuiRenderCoordinator` 的事件缓冲刷新、尺寸读取、模型渲染、backend 提交和状态栏同步逻辑，但绕过正常帧节流/`call_soon` 排队，以便 `_run_conversation` 返回前首帧已经提交。

顺序固定为：

1. 校验当前仍有会话并确认是普通文本提交；
2. 写入待显示用户消息和准备中展示状态；
3. 执行立即渲染并完成 backend 帧提交；
4. 创建任务监督器并注册 TUI 任务；
5. 通过现有事件循环启动监督器，后续恢复标准的事件驱动渲染。

普通的 `schedule_render()` 仍用于后续增量、状态更新和动画。立即渲染只作为提交边界的屏障，避免把全局帧调度改成阻塞模型。

备选方案是只提前发送 `planning` 状态再调用现有 `schedule_render()`，但 `call_soon` 仍可能晚于任务启动，无法形成可测试的先渲染后初始化顺序；因此不采用。

### 3. 以真实事件作为运行态权威并做幂等合并

`SESSION_STARTED` 仍是进入真实会话运行态的唯一事件来源。模型收到该事件时，按现有待显示内容匹配逻辑移除对应待去重标记；匹配成功则保留已经显示的用户块，匹配失败才追加新的用户块。这样首帧反馈不会重复计入用户消息，真实事件中的会话内容仍拥有最终权威。

任务监督器、模型事件处理和协调器的终态清理保持分层：模型事件负责错误/取消/回合结束的可见状态，协调器 `finally` 负责 TUI 任务引用和待提交标记的兜底清理。没有真实开始事件的失败路径必须和已开始会话的失败路径一样可重试，且不能残留“运行中”状态。

### 4. 以时序断言作为回归测试契约

测试 backend 记录每次 transcript/status 渲染，FakeSession 或初始化钩子记录真实 `run()`/客户端准备的开始时刻。测试必须断言首个包含提交反馈的 backend 帧先于真实会话启动；只检查内存 transcript 不足以覆盖该问题。

测试分为三层：模型层验证预回显与真实事件去重，TUI 生命周期层验证首帧顺序和最终状态，交互回归层验证斜杠命令、忙碌态草稿、登录输入、取消和初始化失败没有被普通文本路径改变。

## Risks / Trade-offs

- [首帧渲染期间发生 backend 或尺寸错误] → 立即渲染沿用现有 backend 错误边界；任务启动前不得吞掉异常，失败时由 TUI 统一显示可诊断错误并清理准备态，避免产生不可见的后台任务。
- [预回显消息与真实开始事件内容不一致] → 仅对规范化后的用户内容做匹配；匹配失败时保留真实事件的追加语义，并在测试中覆盖不同内容与连续提交场景。
- [初始化失败导致待去重标记残留] → 在协调器成功、失败、取消和任务创建异常路径集中清理待去重标记，同时保留 transcript 中已经可见的用户消息。
- [立即渲染增加提交路径耗时] → 只增加一次当前视口的同步 backend flush，不执行模型、工具或磁盘 I/O；后续增量仍受原有帧率调度约束。
- [渲染屏障与已有待处理帧交错] → 屏障执行前先处理事件缓冲并明确 `render_pending` 状态，屏障后让调度器继续合并已排队帧，防止旧帧覆盖准备态或重复刷新。

## Migration Plan

1. 先补充模型与 TUI 生命周期回归测试，固定首帧、初始化和终态顺序。
2. 实现待提交准备态、立即渲染屏障及真实事件/失败清理。
3. 运行 TUI 相关窄测试、分层测试、Ruff、`git diff --check` 和 OpenSpec 验证。
4. 该变更没有持久化或公共协议迁移；回滚时移除准备态和屏障调用即可恢复原有异步渲染路径。
