## Context

现有工具层已经有 `resolve_bash`、PATH 扫描、平台进程后端、纯 Python 的 `grep`/`find` 实现和独立安全分类器，但这些判断分散在执行路径中。TUI `/status` 目前只展示运行、上下文、技能和 MCP 诊断。详见 proposal.md 的 Why 和变更范围。

## Goals / Non-Goals

**Goals:**

- 建立不可变、可序列化且与具体 UI 无关的能力快照。
- 复用现有 shell/PATH/平台判断，统一缺失依赖和权限策略的稳定诊断。
- 由工具工厂生成快照，并让 `/status` 在不触发副作用的情况下展示它。
- 让后续 V4-34/V4-35 能复用能力模型，而不需要重新解析文本或重复探测。

**Non-Goals:**

- 不执行 shell、`rg` 或 `fd` 做可用性验证；PATH 和文件可执行性检查就是本变更的探测边界。
- 不改变 `grep`/`find` 的搜索实现，不新增外部依赖，也不在本变更实现 fallback、并发限制、内存上限或 retry。
- 不把能力快照写入 JSONL，不让 core 依赖工具层，也不改变现有工具错误语义。

## Decisions

1. **能力模型放在 tools 层，展示在 app 层。** 能力事实来自工具执行环境，放在 `tools` 可避免 core 反向依赖具体工具；TUI 只消费结构化模型，不在展示层猜测状态。
2. **每项能力使用稳定 key、状态、code、message 和可选 detail。** 这样缺失 Bash、缺失可选检索器和未装配策略可以被测试与 UI 区分；不使用异常文本作为协议。
3. **探测函数接收显式平台、环境和策略是否装配的输入。** 默认使用当前进程环境，但测试可以离线模拟 Windows、PATH 和缺失能力；不会调用真实进程或修改全局 PATH。
4. **工具工厂保留原有返回类型并通过伴随入口暴露快照。** 现有 `make_tools` 调用方不被迫解包新元组；新增 `detect_tool_capabilities` 作为明确的读取入口，后续组合根可同时装配工具和诊断。
5. **能力探测结果在单次构建内冻结。** 使用 frozen dataclass 和 tuple，避免状态栏渲染过程中能力事实被悄悄改变；下一次环境/配置装配重新探测。

## Risks / Trade-offs

- [PATH 在装配后变化] → 快照明确表示装配时事实；后续变更如需刷新必须显式重新探测，不伪装成实时监控。
- [文件存在但不可执行的判断受平台差异影响] → 对外只承诺可探测的 PATH/文件事实，并为未知异常返回独立诊断，不把它升级为工具调用失败。
- [展示新增状态行可能增加 `/status` 长度] → 能力明细使用固定、紧凑分组；完整诊断仍通过信息面板滚动查看。

## Migration Plan

先新增能力模型和离线契约测试，再在工具工厂和 `/status` 接入；现有调用方继续调用 `make_tools` 得到原八工具。回滚时删除能力读取和展示接线即可，不涉及持久化迁移。
