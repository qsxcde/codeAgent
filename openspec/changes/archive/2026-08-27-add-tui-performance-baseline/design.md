## Context

现有 TUI 单元测试覆盖渲染、滚动、命令和 Textual 适配，但只断言行为正确。`TuiModel` 已暴露少量帧与缓存统计，尚未定义统一的计时边界、稳定 fixture、结果格式或基准入口。详见 [proposal.md](proposal.md)。

## Goals / Non-Goals

**Goals:**

- 让同一机器、同一 Python/依赖环境下的 TUI 性能结果可重复比较。
- 分别观测事件归约、模型渲染、后端渲染、Markdown、缓存和内存，而不是只记录总时长。
- 用离线 fixture 覆盖预期热点，并让正常测试套件保持快速、无网络且无机器特定的绝对性能断言。

**Non-Goals:**

- 不采集生产遥测、不上传 prompt、会话内容或密钥。
- 不在本变更中改变渲染算法、缓存策略或用户可见行为。
- 不引入 benchmark 框架、数据库或新的运行时依赖。

## Decisions

### 统一测量边界与结构化结果

定义每个场景的 `event_apply`、`model_render`、`backend_render`、`frame_total`、`markdown_render`、`cache`、`event_count` 和峰值内存指标。结果以 JSON 输出，包含场景参数、重复次数、p50/p95、Python 版本、平台、提交标识（可用时）和命令行参数。

选择标准库 `time.perf_counter` 与 `tracemalloc`，避免增加依赖；以毫秒记录时延，以计数记录工作量。相较于只测完整 TUI，分段计时可以区分布局、富文本转换和具体后端成本。

### 纯组件优先的离线场景

基准主路径使用 `TuiModel`、Transcript、假 backend 和脚本化事件，不启动真实 Textual，也不请求模型。场景至少包括历史 block 数量、流式正文长度、工具输出、滚动、resize 和恢复构建。

真实 Textual 只保留小范围适配测试，不作为稳定性能基准，以避免终端尺寸和事件循环调度造成不可比较的噪声。

### 基准与普通回归测试分离

普通 pytest 只断言事件顺序、缓存失效、工作量上界和结果格式；可重复计时通过显式 benchmark 命令运行。这样不会让 CI 因机器差异失败，同时仍能防止已知的全量历史重绘回归。

### 结果归档而非硬编码全局阈值

提供可指定输出路径的 benchmark 命令和文档化结果格式。初始阶段记录基线；后续优化在相同环境和场景下做相对比较。绝对 33ms 等目标作为审查参考，不作为跨机器的唯一门禁。

## Risks / Trade-offs

- [微基准偏离真实终端行为] → 场景同时包含模型层、假 backend 和少量 Textual 适配回归，并明确结果适用边界。
- [计时噪声掩盖小改动] → 每个场景重复多次，记录分位数与工作量计数，不只比较单次结果。
- [基准过慢影响开发] → 基准从默认 pytest 路径分离，测试 fixture 保持小规模。
- [结果文件泄露会话内容] → fixture 只使用合成文本；结果只写指标和环境元数据。

## Migration Plan

1. 增加测量数据结构、假 backend 和合成 fixture。
2. 增加显式 benchmark 入口与 JSON 结果校验。
3. 记录当前基线并更新 v0.4 文档。
4. 后续优化变更复用相同场景和结果格式；如需回滚，删除观测代码和文档即可，不影响运行时行为。
