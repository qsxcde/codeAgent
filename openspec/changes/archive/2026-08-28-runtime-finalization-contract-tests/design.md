## Context

参见 `proposal.md`。当前 `Agent` 能在 core 内部成功后提交内存上下文，但 `AgentSession.run()` 在 Runtime 收尾后才执行 JSONL 提交和自动压缩，提交异常因此不一定进入统一失败路径。测试已有多轮 ReAct、工具并发和基础取消覆盖，但缺少对事务式收尾和事件终态的系统验证。

## Goals / Non-Goals

**Goals:**

- 固定执行结果、消息历史、usage、持久化和压缩之间的提交顺序。
- 失败或取消时提供可验证的消息与 usage 隔离。
- 对 Runtime 的关键状态和事件契约建立可重复、离线、跨平台测试矩阵。
- 确认成功收尾之后的继续、恢复和分叉仍使用一致历史。

**Non-Goals:**

- 不在本变更中新增测试框架、CI 平台或真实 provider 测试。
- 不改变 JSONL append-only 格式和既有历史数据结构。
- 不以全量测试替代针对状态边界的契约测试；全量测试仍由发布阶段执行。

## Decisions

### 1. 使用显式 RunOutcome 驱动收尾

执行器返回成功、失败或取消的结构化结果，session 依据结果决定提交或回滚。提交、usage 和压缩失败也转换为失败结果，并沿用同一终态事件路径，而不是让异常从 `finally` 外部逃逸。

### 2. 消息和 usage 采用两阶段提交语义

运行期间只在工作列表中积累新消息和 usage；成功路径先完成消息和 usage 的一致性提交，再更新可继续使用的内存历史；失败路径不追加任何未完成轮次 entry。若底层 store 无法提供真正事务，则通过提交前构造完整 entry、失败不更新内存游标和回放校验来保持可恢复语义。

### 3. 测试按行为矩阵组织

测试分为 core loop、runtime boundary、session persistence 和 integration-like contract 四组。每个场景使用 FakeClient、可控工具、注入的 store 和事件收集器，不访问真实网络或用户配置目录。

### 4. 先窄测再全量测

每个任务先运行受影响的测试文件和标记，再由用户或 CI 执行全量测试。测试名称描述行为和终态，断言优先读取结构化字段，不解析人类可读错误文本。

## Risks / Trade-offs

- **[Risk]** append-only 存储无法对多条 entry 提供数据库式原子事务 → 先在内存中完成一致性校验，按固定顺序追加，并为部分写入恢复增加回归测试。
- **[Risk]** 自动压缩失败可能发生在消息提交之后 → 将压缩作为独立收尾阶段记录明确结果，不能删除已成功提交的消息，也不能重复提交 usage。
- **[Risk]** 测试 fixture 过度模拟真实工具 → 保留少量 subprocess/MCP 资源边界测试，主要逻辑仍使用可控 fake tool 以保证跨平台稳定。
- **[Risk]** 事件数量增加造成测试脆弱 → 测试使用关键事件序列和稳定字段断言，允许非关键进度事件扩展。

## Migration Plan

1. 先补充提交失败、压缩失败和终态唯一性的失败测试，确认当前缺口。
2. 调整 AgentSession 的成功提交和失败回滚边界，使测试通过。
3. 补充取消、监听器异常、配置透传和恢复/分叉回归测试。
4. 使用窄测试、OpenSpec 校验和 CI 质量门禁验证，最后由用户执行全量测试。

回滚时可以保留新增测试并撤回收尾实现；不需要迁移已有 JSONL 文件。
