## Context

模型请求目前由 OpenAI 兼容传输层负责，工具执行发生在核心编排收到完整模型响应之后。Provider 错误已经有统一分类和 `retry_after` 元数据，但传输层仍直接计算退避，最大重试次数也没有严格边界；session 层不能依赖 `ai` 包，因此需要通过稳定属性识别 Provider 错误。

## Goals / Non-Goals

**Goals:**

- 将重试次数校验、退避上限和 `Retry-After` 处理收敛到可测试的传输层策略。
- 保持流式请求的“首事件前可重试、首事件后不重放”语义。
- 让 session runtime 保留 Provider 的错误分类和可重试语义，同时不破坏现有 core/session 依赖方向。
- 以回归测试证明模型重试不会重复执行工具。

**Non-Goals:**

- 不修改 core 工具执行循环、工具协议或会话持久化格式。
- 不为工具执行增加自动重试，也不把未知副作用变成可重试。
- 不引入随机抖动、外部重试库或新的配置文件格式。

## Decisions

### 1. 使用独立的纯策略模块

在 `ai/transport/retry.py` 中提供最大重试次数校验和退避计算。策略使用固定的系统上限，优先采用已解析的 `retry_after`，否则使用指数退避；不引入随机抖动，以便离线测试和问题复现保持确定性。

备选方案是继续在两个传输方法中内联计算，但会让流式和非流式边界逐渐分叉，也难以单独验证配置约束。

### 2. 在 Provider 错误分类之后决定是否重试

传输层继续使用 V4-36 的 `ProviderError` 分类结果作为唯一重试依据，并把 `retry_after` 交给统一策略。这样认证、请求参数和未知错误不会因为 HTTP 状态或异常类型的粗粒度判断而被误重试。

### 3. 保留流式首事件保护

流式循环继续记录是否已经向调用方产出事件；只有首事件之前的失败可以重新建立连接。首事件之后直接抛出分类错误，避免重复文本、推理增量或工具调用增量。工具执行仍在流式聚合完成后的 core 边界之外。

### 4. Session 采用最小结构化兼容识别

`session/runtime/error_classification.py` 不导入 `codeagent.ai`，而是读取 Provider 错误公开的 `kind`、`retryable`、`provider` 等属性，并对未知对象保持旧的 httpx/运行时映射。这遵守 session 不依赖 AI 具体实现的架构约束，同时允许 Provider 错误向用户呈现稳定的错误代码。

## Risks / Trade-offs

- [模型服务接受请求后连接中断] → 非流式路径只有收到完整响应才进入工具执行；流式路径首事件后禁止重放，并由 TUI 展示部分结果和失败。
- [退避时间过长影响交互] → 对 `Retry-After` 和指数退避统一设置上限；取消仍由现有 async 请求和会话生命周期处理。
- [第三方 Provider 返回不规范的错误] → 继续使用 V4-36 的安全截断和分类兜底，未知分类不自动重试。
- [session 与 Provider 解耦导致字段缺失] → 结构化属性均采用兼容读取，缺失时保留既有错误代码和消息行为。

## Migration Plan

1. 先加入策略和会话分类的离线回归测试，再替换传输层内联退避。
2. 运行 AI、session、core 相关窄测试及完整离线测试，确认既有 `HTTPStatusError` 兼容性。
3. 更新 v0.4 文档和 OpenSpec，完成后归档变更；不需要数据迁移或回滚脚本。

## Open Questions

无。重试上限、流式边界和工具副作用边界已经由规格固定。
