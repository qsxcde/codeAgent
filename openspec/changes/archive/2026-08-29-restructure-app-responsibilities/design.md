## Context

见 [proposal.md](proposal.md)。现有架构测试已限制 `app` 的跨层依赖，但 `textual_backend.py`、`command_coordinator.py`、`session_coordinator.py`、组合工厂、技能包和任务模块仍同时承担多个独立状态机或适配职责。`AGENTS.md` 要求生产文件原则上不超过 300 行、函数不超过 50–80 行，并要求失败路径保留完整诊断上下文。

## Goals / Non-Goals

**Goals:**

- 将应用层代码收敛为职责明确、单向依赖、可独立测试的模块；本次触及的生产文件满足规模规范。
- 保持既有入口、命令、渲染输出、会话持久化和运行时事件语义不变。
- 让每个已处理的失败路径同时具备安全的用户提示与包含上下文的日志诊断。

**Non-Goals:**

- 不改变 CLI/TUI 命令集合、Textual 布局、模型或工具协议、会话 JSONL 格式。
- 不引入新的终端引擎、依赖注入框架或全局 service locator。
- 不机械地按文件大小拆分小型内聚模块；拆分必须对应稳定的职责或依赖边界。

## Decisions

### 使用“职责子包 + 短外观”而非一次性的大规模改名

TUI 按展示、交互命令、会话操作和运行时调度分组；组合层按模型、工具、TUI 和跨层装配分组；技能与任务按发现/安装、监督/验证分组。原有被其他应用模块或测试导入的路径在迁移期间保留短外观或显式 re-export，随后仅在确认无内部依赖时删除。

相较于仅切分函数而保留原大文件，这能让依赖方向可被测试；相较于重命名整个目录树，这能降低导入迁移和回滚风险。

### 顶层协调器只拥有生命周期，具体状态归属到专门组件

`TuiApp`、工厂和任务入口保留显式依赖注入、回调注册与关闭顺序。输入解析、命令分派、会话切换/恢复、渲染帧调度、Transcript/视图状态、模型配置转换、技能包安装和任务验证分别由窄接口的协作者管理。

禁止将新协作者放入模块级单例或共享可变字典。这样避免把大文件替换为新的“服务管理器”上帝对象，并使 fake backend/fake session 的单元测试继续可用。

### 具体引擎与跨层适配留在边缘

Textual 类型只能出现在 Textual backend 及其展示适配模块；TUI 协调代码只依赖 backend 端口和核心/会话事件。`composition/` 是唯一负责连接 `ai`、`tools`、`session` 与 TUI/CLI 的区域，`app` 的其余模块不得重新实现提供商、工具或会话基础设施逻辑。

保留并扩展现有 AST 导入测试，而不以运行时约定代替静态边界；这比依赖代码评审更稳定，也比引入 DI 容器更符合当前项目规模。

### 统一应用层错误呈现与诊断

提取小型错误报告帮助器或注入式 reporter：调用点提供操作和安全对象标识；reporter 使用标准 logger 记录异常上下文（含 traceback），再向 CLI/TUI 显示不含敏感信息的用户消息。仅用于预期控制流的异常仍显式捕获并保持现有语义。

不采用无差别 `except Exception: pass` 或只更新 UI 状态的模式；也不把原始异常文本直接显示给用户，以避免泄漏凭据、路径或提供商响应。

### 以行为基线和规模检查保护迁移

先补齐 fake backend、fake client 与 fake session 的特征测试，再按职责迁移。架构测试校验允许的依赖方向；新增或扩展 AST 规模检查覆盖变更涉及的应用生产模块，确认文件不超过 300 行、函数不超过 80 行（必要兼容外观除外，并须在测试白名单中注明理由）。

这比一次性全量移动后再调试更能定位行为回归，也避免将历史遗留超规模文件永久排除在规范外。

## Risks / Trade-offs

- [拆分期间形成循环导入] → 先抽取仅含协议、数据类型或纯函数的低层模块；每批迁移运行导入边界测试。
- [兼容外观掩盖旧依赖而长期存在] → 在任务中显式迁移生产/测试导入，最后扫描并删除不再需要的外观。
- [TUI 状态或事件顺序发生细微回归] → 迁移前固化 fake backend 的输入、命令、会话、取消、恢复与渲染回归场景。
- [日志包含敏感内容] → reporter 只接受操作与安全标识；异常详情写入受控日志，不直接投影到 UI。
- [规模检查诱导过度拆分] → 只为独立状态机、依赖边缘或可测试算法建立模块；对确有必要的短兼容层记录例外原因。

## Migration Plan

1. 建立职责映射、特征测试、错误报告约定与 AST 护栏，不改变运行时行为。
2. 按 TUI 展示/调度、交互/会话、组合工厂、技能、任务的顺序迁移；每个阶段保持短外观并运行对应窄测试。
3. 迁移所有内部导入，删除无用外观，检查没有具体引擎或基础设施依赖越过边界。
4. 更新架构文档，执行分层测试、完整离线测试、Ruff、差异检查和规模扫描。
5. 若出现行为回归，以单个职责迁移提交回退；由于不改持久化格式和公共入口，不需要数据迁移或兼容转换。
