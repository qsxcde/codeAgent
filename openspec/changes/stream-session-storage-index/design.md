## Context

现有文件后端以每个会话一个 JSONL 文件保存 append-only 历史；公共 `SessionStore` 协议、`MemoryStore` 和现有 JSONL 格式都需要保持兼容。当前内部迭代器通过 `read_text().splitlines()` 读取文件，部分调用方又把所有 entry、message 或待写行复制到列表中。具体动机见 `proposal.md`，行为要求见 `specs/sessions/spec.md`。

## Goals / Non-Goals

**Goals:**

- 使用真正的逐行解析，避免元数据、用量、上下文恢复和分叉路径产生完整原始文本及完整 entry 副本。
- 为稳定的会话元数据和用量查询提供轻量、可校验、可重建的本地索引缓存。
- 让上下文恢复和分叉在内存受控的前提下保持现有压缩、目标消息和父子会话语义。
- 在索引不可用、损坏或更新失败时，始终可以回退到 JSONL 的直接流式读取。

**Non-Goals:**

- 不把 JSONL 迁移为数据库，也不新增第三方依赖。
- 不构建完整逐消息随机访问索引，不改变公开 `SessionStore` 协议或 `MemoryStore` 实现。
- 不引入仓库索引、RAG 或其他与会话存储无关的检索能力。
- 不为实现“最后更新时间”而修改每条 entry 的格式；初版使用源文件大小与纳秒级修改时间等文件指纹。

## Decisions

### 1. JSONL 继续作为唯一真相源，索引只是私有缓存

在会话目录中为每个 JSONL 文件维护对应的私有 `.index.json` 摘要文件。索引包含会话列表和用量查询所需的结构化摘要，例如标题、最新模型配置、父会话、工作目录、会话创建信息、源文件指纹、用量聚合、最近一次压缩切点以及必要的最后元数据值；不复制完整消息正文或压缩摘要。

读取索引前先比较源文件指纹（至少包括文件大小和 `st_mtime_ns`，不可用时使用平台可用的更稳定组合）。指纹不匹配、索引 JSON 无法解析或字段版本不兼容时，直接从 JSONL 流式重建。索引写入使用同目录临时文件加原子替换，并沿用会话目录的权限策略。

选择可重建缓存而不是 SQLite 或完整历史索引，是为了不增加迁移、锁、依赖和隐私面；选择摘要而不是逐消息偏移索引，是因为 P1-1 的主要收益来自避免重复全量解析，而不是提供任意消息随机访问。

### 2. 追加成功优先于索引更新

现有路径锁继续保护 JSONL 追加和会话级并发。写入操作先完成 JSONL 追加，再尝试增量更新索引；索引更新失败不得撤销已经成功的会话写入，也不得阻塞后续读取。更新失败时删除或标记索引为过期，让下次读取通过流式扫描重建。

创建会话、追加消息、元数据、模型变更、用量和压缩记录都需要更新相应摘要。外部修改或进程崩溃造成的漂移由下一次指纹校验发现。索引内容不作为恢复消息、压缩摘要或其他业务真相使用；需要这些内容时仍从 JSONL 读取。

### 3. 用单一内部逐行迭代器替换全量读取

内部迭代器使用文本文件句柄逐行读取并立即解析 JSON。它保留现有空行跳过、非法 JSON 行跳过、header/version 校验和结构性错误处理；只把当前 entry 交给调用方。`_read_entries` 这类把迭代器包成完整列表的路径应从元数据、用量、上下文和分叉调用方移除，而不是只在底层增加一个新的包装器。

`load_messages` 的公开返回值本身是完整消息列表，因此允许保留调用者要求返回的消息；但实现不得同时保留原始文本、分行数组或完整 entry 列表。元数据和用量聚合只保留固定大小的累计状态。

### 4. 上下文恢复按压缩切点流式保留消息

恢复流程先取得最近压缩记录及其切点：优先使用通过指纹校验的索引元数据，缺失或不可信时流式扫描。随后逐行扫描有效消息，只把切点之后需要恢复的消息放入返回列表，并单独保留压缩摘要；物理历史中的切点前消息不进入完整中间列表。这样保留现有“压缩摘要加压缩后消息”的恢复语义，同时避免 `all_messages` 和完整 entry 列表的重复峰值。

### 5. 分叉采用必要时的两遍流式扫描

分叉需要保持“复制到目标 user 消息之前”以及“复制最近压缩状态”的既有语义。为避免把完整源历史放入内存，采用两遍扫描：第一遍校验 header、定位目标 user 消息并记录最近压缩记录及其切点；第二遍重新打开源文件，按目标边界和压缩语义逐行读取，并直接写入新文件。新文件只持有当前输入行和必要的固定大小状态，源文件保持不变。

两遍扫描会增加分叉场景的磁盘读取次数，但分叉不是每轮会话恢复的热路径，换取的是与会话长度无关的辅助内存。若目标消息需要先由 `SessionManager` 推导，`load_messages` 的既有 API 仍可返回消息列表；文件后端自身的 fork 复制过程不得再构造完整 `entries`、`messages` 和 `lines` 副本。

### 6. 索引只优化可安全缓存的查询

`list`、`get` 和 `load_usage` 在索引有效时直接读取摘要；任何索引读取、指纹校验或字段转换异常都回退到直接流式扫描。涉及消息正文、压缩摘要恢复和分叉内容的操作继续以 JSONL 为依据。文件修改时间只用于缓存新鲜度和列表排序等已有元数据展示，不改变消息语义，也不要求新增逐 entry 时间字段。

## Risks / Trade-offs

- **索引与 JSONL 短暂漂移** → JSONL 写入优先；以大小和修改指纹校验，索引异常时重建，重建失败时直接流式读取。
- **进程在追加与索引替换之间崩溃** → 下次读取发现指纹不一致并重建；原子替换避免产生半个索引文件。
- **并发追加导致索引更新竞态** → 复用现有会话路径锁；索引更新失败时使缓存失效，不把缓存当作真相源。
- **文件系统修改时间精度不足** → 优先使用 `st_mtime_ns` 并同时比较文件大小；无法可靠判断时宁可流式重建。
- **索引泄露会话元数据** → 索引不保存完整历史或摘要正文，使用会话目录同等的私有权限，并允许随时删除后重建。
- **分叉两遍扫描 I/O 增加** → 将额外读取限制在 fork 路径，以有界内存换取可接受的非热路径成本。
- **保留消息列表的上下文本身仍可能增长** → 这是现有恢复 API 的必要结果；本设计只移除物理历史和中间副本，不改变上下文截断策略。

## Migration Plan

1. 首次读取或写入已有会话时，发现没有索引即可按当前 JSONL 格式流式扫描并惰性创建 `.index.json`；不需要迁移或重写任何 JSONL 文件。
2. 新建会话及后续追加在 JSONL 成功后增量维护索引；旧索引缺失、损坏、版本不兼容或指纹过期时按第 1 步重建。
3. 回滚实现时可删除对应 `.index.json`，系统仍通过 JSONL 直接读取；回滚不触碰会话历史文件。
4. 测试覆盖无索引旧会话、索引更新失败、外部修改和损坏索引，确认所有场景都能回退到直接流式读取。
