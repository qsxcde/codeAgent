# CodeAgent 项目成熟度与完善度评估报告

> 评估日期：2026-08-24  
> 评估范围：当前代码树、测试、CI、设计文档与已落地的 v0.3 能力  
> 评估目的：判断项目距离“完善的代码智能助手”还有多大差距，并给出可执行的建设顺序。

## 1. 执行摘要

CodeAgent 已经超过概念验证阶段，当前更准确的定位是：**具备完整基础闭环的单用户 Coding Agent Beta**。

项目已经具备模型接入、流式对话、自研 ReAct 编排、工具调用、安全确认、会话持久化、上下文压缩、TUI、MCP 和 Skill Package 等能力。架构层面也形成了较清晰的端口-适配器分层，核心编排层可以离线测试。

但项目距离“完善”仍有明显差距，差距主要不在基础设施，而在以下四项：

1. **真实编码任务的可靠闭环**还不完整：计划、修改、测试、失败分析、修复、复核尚未形成稳定工作流。
2. **代码仓库理解能力**仍以文件和文本工具为主，缺少索引、符号、AST/LSP 和结构化 Git 能力。
3. **安全边界**目前主要依赖命令分类和确认策略，还不是进程级或容器级隔离沙箱。
4. **产品化和质量门禁**仍不完整：缺少真实任务评测、覆盖率、静态检查、构建安装冒烟、多平台发布验证等。

基于能力成熟度的粗略判断如下。百分比不是代码覆盖率，而是相对于目标产品形态的主观成熟度估算：

| 目标形态 | 当前完成度判断 |
| --- | ---: |
| 可供个人开发者试用的 CLI/TUI 内测版 | 约 80% |
| 稳定的单用户发布版 | 约 60%～70% |
| 对标 Codex / Claude Code 的完整产品 | 约 35%～45% |

如果目标是个人日常使用，项目已经到了“集中补可靠性即可投入使用”的阶段；如果目标是公开发布或对标成熟 Coding Agent，则仍需要一轮以可靠性、安全性、仓库理解和工程化为中心的建设。

## 2. 评估口径与证据

本报告中的“完善”不是指无限增加功能，而是指一个代码助手至少能够稳定完成以下闭环：

```text
理解任务 → 制定计划 → 检索仓库 → 修改代码 → 运行验证 → 分析失败 → 修复重试 → 汇报变更
```

同时需要满足：

- 会话可恢复，恢复后上下文和状态一致；
- 工具执行可控、可取消、可审计；
- 破坏性操作有明确的安全边界；
- 在常见真实任务上有可重复的质量评测；
- 用户可以安装、升级、诊断和卸载；
- 新版本有自动化质量门禁，而不是只依赖人工检查。

主要证据来源：

- `src/codeagent/core/loop.py`：自研 ReAct 主循环、工具执行、确认环和递归限制。
- `src/codeagent/session/session.py`、`src/codeagent/session/store.py`：会话历史、持久化、恢复、用量和压缩状态。
- `src/codeagent/tools/registry.py`、`src/codeagent/tools/security.py`：内建工具和安全策略。
- `src/codeagent/app/skill_packages.py`、`src/codeagent/app/skill_runtime.py`：Skill Package 管理和 CodeAgent 适配器。
- `src/codeagent/app/tui/view.py`、`src/codeagent/app/tui/components.py`：TUI 交互和渲染。
- `.github/workflows/ci.yml`：当前 CI 质量门禁。
- `README.md`、`CLAUDE.md`、`docs/design/`、`docs/iteration/`：项目目标、范围和已知未实现能力。

## 3. 当前能力盘点

### 3.1 已经具备的能力

| 能力域 | 当前实现 | 成熟度判断 |
| --- | --- | --- |
| Agent 编排 | 自研异步 ReAct 循环，支持流式文本、思考事件、工具调用、工具结果、取消、注入消息和递归限制 | 较强 |
| 模型接入 | DeepSeek、OpenAI、Qwen、GLM、Kimi、MiniMax、Fake；统一 OpenAI 兼容传输；支持重试和 usage 透传 | 较强 |
| 基础工具 | `read`、`write`、`edit`、`bash`、`grep`、`find`、`ls`、`skill` 八个内建工具 | 可用，但偏基础 |
| MCP | 支持 server 配置、工具发现、命名空间、调用超时和预算控制 | 可用 |
| 会话 | JSONL append-only 持久化、恢复、切换、fork、会话树和成功轮次才落盘 | 较强 |
| 上下文 | token 用量累计、上下文窗口展示、摘要压缩、压缩状态恢复 | 可用，估算仍较粗 |
| TUI | 斜杠命令、补全、模型切换、登录、会话管理、工具块、Markdown、上下文状态栏 | 可用，仍属 MVP/内测级体验 |
| Skills | 内建/用户/项目发现、优先级、按需加载、Package 安装和 Bootstrap Skill | 较强，但能力适配不完整 |
| 安全 | bash deny/ask/allow、敏感命令确认、文件访问边界、headless 默认 fail closed | 有基础，但尚未达到强隔离 |
| 可测试性 | Fake Provider、内存文件系统、分层解耦测试、核心模块离线测试 | 结构较好 |

### 3.2 当前项目最有价值的资产

1. **架构边界比较清楚。** `core` 不依赖具体模型、工具或会话实现，组合根集中在 `app/container.py` 和 `app/main.py`，这为后续增加工具、模型和运行时提供了扩展空间。
2. **会话被当作状态管理，而不是一次性请求。** 这使恢复、分叉、压缩和上下文展示具备了统一基础。
3. **事件驱动接口已经形成。** CLI、TUI、测试和 CI 都可以通过事件订阅获得运行过程，而不是只能拿最终字符串。
4. **Skills 和 MCP 的接入方向正确。** 内容型 Skill 与外部工具能力分离，缺失能力会被显式声明，而不是伪造不存在的工具。
5. **安全问题已经被纳入架构。** 当前仍不完备，但已经不是“工具直接执行、没有确认环”的早期形态。

## 4. 与完善形态的主要差距

### 4.1 P0：必须补齐的可靠性能力

#### 4.1.1 缺少稳定的编码任务闭环

当前循环的基本模式是“模型调用 → 工具执行 → 再次调用模型”。这能支撑简单任务，但尚未在 Agent 层固化以下行为：

- 修改前明确任务计划和影响范围；
- 修改后自动运行相关测试或检查；
- 测试失败后读取失败上下文并重试修复；
- 最终检查工作区 diff，确认没有意外改动；
- 明确区分“已完成”“部分完成”和“无法验证”。

现有 `RecursionLimitError` 可以防止模型无限调用工具，但它只是停止机制，不是任务完成机制。换言之，当前 Agent 可以“执行很多步骤”，但还不能稳定保证“完成正确结果”。

#### 4.1.2 仓库理解仍以文本检索为主

现有工具覆盖文件读写、文本搜索、glob 查找和 shell，但没有：

- 仓库级文件/符号索引；
- 函数、类、引用和调用关系查询；
- AST 级结构化编辑；
- LSP 诊断、跳转定义和类型信息；
- 变更影响范围分析。

对小型项目影响有限，但在中大型代码库中，Agent 会更依赖反复 `grep` 和模型推断，准确率和效率都会下降。

#### 4.1.3 Git 能力没有结构化

Git 目前主要通过 `bash` 间接使用。缺少结构化的：

- 工作区状态和变更摘要；
- patch/diff 审查；
- checkpoint、undo 和安全回滚；
- 分支、提交、worktree 生命周期管理。

这会直接影响“改错后恢复”和“用户审查 Agent 改动”的体验。

#### 4.1.4 安全策略不是完整沙箱

`src/codeagent/tools/security.py` 已经提供命令分类、文件边界和确认策略，但 bash 最终仍在宿主机进程中执行。当前缺少：

- 进程级/容器级隔离；
- 独立的网络权限控制；
- 更细粒度的环境变量和凭据脱敏；
- 完整的执行审计记录；
- 文件、进程、网络资源的统一权限模型。

因此，当前安全能力适合个人使用和显式确认场景，不应直接等同于生产级沙箱。

### 4.2 P1：决定产品体验的能力

#### 4.2.1 上下文压缩仍是近似实现

当前压缩模块使用字符数除以 4 估算 token，能满足离线和跨供应商的简单场景，但不是精确 tokenizer。长会话、不同语言、工具输出非常长或模型上下文窗口较小时，可能出现估算偏差。

此外，摘要质量依赖外部 `Summarizer`，还缺少摘要质量的自动评测和失败后的降级策略。

#### 4.2.2 Skill 运行时能力仍不完整

Skill Package 的内容发现、安装和生命周期已经可用，但 `CodeAgentAdapter` 明确标记了 subagent、todo 和 web 等能力不可用。对于依赖这些能力的外部 Skill，当前只能使用其降级路径。

这意味着当前已具备“引入 Skill 内容”的能力，还没有完全具备“执行任意成熟 Agent Skill 工作流”的能力。

#### 4.2.3 TUI 仍是开发者工具级体验

TUI 已覆盖主要工作流，但仍需要持续打磨：

- 长输出、超长 Markdown 和终端 resize 的稳定性；
- 运行中错误、取消和重试的交互反馈；
- 命令发现、帮助、快捷键和状态层级；
- 会话切换时的加载状态和恢复提示；
- 大型会话的渲染性能和可滚动性。

这些问题不一定阻塞核心功能，但会明显影响日常使用的“产品感”。

#### 4.2.4 模型运行治理不足

当前已经有 HTTP 重试和多 provider，但仍缺少：

- provider/model 自动故障转移；
- 速率限制与并发控制；
- 预算和配额保护；
- 基于模型能力的任务路由；
- 更完整的请求、失败和延迟可观测性。

### 4.3 P2：从本地工具走向平台的能力

根据当前项目文档，以下功能尚未实现或被推迟：

- 轻量记忆；
- Web/HTTP/SDK 入口；
- 插件运行时；
- 多智能体或 subagent；
- 后台任务和自动化；
- IDE 集成；
- 费用估算。

这些不是个人 CLI/TUI 助手的必需项，但如果目标是完整 Agent 平台，它们会成为明显差距。

## 5. 工程化成熟度评估

### 5.1 已有基础

- 测试按 `ai`、`core`、`session`、`tools`、`mcp`、`tui` 等模块组织。
- Fake Provider 和内存依赖使核心逻辑可以离线测试。
- 分层依赖规则由 AST 测试强制检查。
- CI 已覆盖测试、版本一致性、补丁格式和 OpenSpec 校验。
- 最近一次有效全量回归记录为 703 项通过。

### 5.2 尚未形成的工程门禁

当前 CI 尚未覆盖：

- pytest-cov 覆盖率测量与阈值；
- Ruff、mypy、Black 等静态检查；
- 构建后安装和命令行冒烟测试；
- Windows/Linux/macOS 矩阵；
- 真实模型的契约测试；
- 真实编码任务评测；
- 发布包、配置迁移和升级回滚验证。

另外，README 和 CLAUDE.md 中仍保留“666 项测试”的旧基线，文档状态已经落后于当前测试数量。这属于质量治理问题，虽然不直接影响运行，但会降低项目可信度。

## 6. 分阶段建设路线

### 阶段一：稳定单用户发布版

目标：让 Agent 能够可靠完成常见的小型和中型代码任务。

建议顺序：

1. 在核心循环外增加任务级执行器：计划、实施、验证、修复、总结。
2. 增加测试命令识别和测试失败后的自动修复重试。
3. 增加结构化 Git status/diff/checkpoint/undo。
4. 增加工具取消、子进程清理、失败重试和状态恢复。
5. 强化 bash、网络和密钥的隔离与审计。
6. 建立真实任务评测集，并将关键场景纳入 CI 或夜间评测。
7. 增加覆盖率、静态检查、安装冒烟和多平台 CI。

完成标志：

- 常见修改任务可以自动完成并通过对应测试；
- 测试失败后能自动回到可解释的修复流程；
- 用户能在执行前后审查和恢复变更；
- 失败不会造成会话或工作区状态损坏；
- 质量门禁不再只依赖单元测试。

### 阶段二：增强仓库理解和日常体验

建议建设：

- 仓库文件/符号索引；
- AST/LSP 适配；
- 结构化 Git 工作流；
- 更准确的 token 计算和摘要质量评测；
- Skill 自动选择、来源诊断、信任和更新策略；
- TUI 长任务、错误恢复和大输出优化；
- provider 故障转移、预算和并发控制。

完成标志：

- Agent 能直接回答“定义在哪里、谁调用了它、修改会影响什么”；
- 大型仓库中检索次数显著减少；
- 常见 Git 操作不需要模型拼接 shell 命令；
- 用户能清晰理解当前上下文、成本和执行状态。

### 阶段三：平台级能力

按真实需求再考虑：

- subagent/多智能体；
- 后台任务和自动化；
- 记忆系统；
- Web/HTTP/SDK；
- IDE 和远程执行；
- 更完整的插件运行时。

这一阶段不应早于阶段一完成，否则会在核心可靠性尚未稳定时扩大系统复杂度。

## 7. 时间与投入估算

以下按一名熟悉项目的全职开发者估算，实际时间取决于是否复用现有组件：

| 目标 | 估算投入 |
| --- | ---: |
| 内测版稳定性修补 | 1～2 周 |
| 稳定单用户发布版 | 4～8 周 |
| 增强仓库理解和产品体验 | 6～12 周 |
| 对标成熟 Coding Agent 的平台能力 | 3～6 个月以上 |

其中最不确定的部分是“真实任务可靠性”。增加工具数量通常比较快，但让 Agent 在真实代码库中稳定完成任务，需要评测集、失败样本和多轮迭代，不能只按代码行数估算。

## 8. 最终结论

CodeAgent 当前的优势是基础架构已经成型，核心闭环已经跑通，且会话、Skills、MCP、TUI 和安全策略都不是空壳。它已经可以作为个人开发者的实际 Coding Agent 使用。

当前最重要的工作不是继续堆叠更多命令或外部 Skill，而是把以下闭环做实：

```text
正确理解任务
  → 有计划地修改
  → 自动验证
  → 失败后修复
  → 审查 diff
  → 可回滚、可解释地结束
```

完成这条主线后，项目可以从“功能完整的 Agent Beta”进入“稳定的单用户代码助手”阶段；之后再根据真实用户需求决定是否投入多智能体、记忆、Web 和自动化等平台级能力。
