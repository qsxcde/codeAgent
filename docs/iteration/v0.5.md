## 1. 当前基线

### 1.1 项目状态

v0.4 已完成单 Agent Runtime 的功能范围，运行时、上下文治理、Session/TUI、工具和 Provider 稳定性已经形成较完整的本地 Agent 闭环。当前项目仍然是单用户、本地、离线优先的 Agent，尚未提供真正的多 Agent 或 Subagent 运行时。

| 能力 | 当前状态 | v0.5 关系 |
|---|---|---|
| Agent 编排 | ✅ 已具备 | 复用现有 ReAct 循环，不引入第二套编排框架 |
| AgentSession | ✅ 已具备 | 作为父、子运行的会话外壳，分别实例化 |
| 生命周期 | ✅ 已具备 | 复用 `RunPhase`、取消、资源清理和事件机制 |
| 工具端口 | ✅ 已具备 | 将 `delegate` 作为一个 `AgentTool` 注入父 Agent |
| 上下文预算 | ✅ 已具备 | 为父子运行分别设置预算，并增加委派预算 |
| 会话分叉 | ✅ 已具备 | 继续表示历史分支，不改作 Subagent 调度器 |
| TUI 状态与事件 | ✅ 已具备 | 增加父子运行关联和委派进度展示 |
| Subagent 运行时 | ❌ 未实现 | v0.5 的核心交付 |
| 多 Agent 并行协作 | ❌ 未实现 | 不作为 v0.5 MVP 完成条件 |

### 1.2 工程事实

- v0.4 功能范围 V4-01～V4-38 已完成；发布包版本已统一为 `0.4.0`，发布说明已固定，正式发布标签仍属于发布收尾工作。
- 当前本地全量测试基线为 `1532 passed`（2026-08-30，macOS）；OpenSpec 主规格为 `20/20`；当前无活动 OpenSpec 变更。
- `core/` 保持纯内存、provider-neutral，不直接依赖 `config`、`ai`、`tools` 或 `session`。
- `app/composition/` 是跨层装配边界，负责模型、工具、策略、Session 和运行时资源的组合。
- `SessionManager` 当前是单活会话管理器；`create()`、`switch()` 和 `fork()` 具有当前会话切换语义，不能直接作为父 Agent 的子任务调度器。

### 1.3 当前缺口

当前 Agent 可以在一个会话中执行多轮模型和工具调用，但不能把一个复杂任务委派给另一个拥有独立上下文和生命周期的 Agent。若直接把子任务文本追加到父上下文，会导致上下文膨胀、权限继承不透明、子任务失败难以区分以及 TUI 无法解释父子运行关系。

## 2. v0.5 定位与目标

### 2.1 版本定位

v0.5 的主题是：

> 让父 Agent 可以安全地委派边界明确的子任务，由独立的子 Agent 进行探索或执行，再由父 Agent 基于结构化结果完成综合。

Subagent 在模型侧表现为一个 `delegate` 工具，在运行时侧表现为一个独立的子 Agent 执行单元；“工具接口”与“Agent 生命周期”是两层不同的概念。

### 2.2 用户价值

用户处理复杂问题时可以看到：

1. 父 Agent 自动拆分适合独立处理的子任务；
2. 子 Agent 在不污染主会话的上下文中进行搜索、阅读、分析或验证；
3. 子 Agent 的执行阶段、耗时、失败和取消状态清晰可见；
4. 父 Agent 将多个子任务结果整理成一份统一答案；
5. 子 Agent 的权限、预算和工作区范围受到明确限制，用户不会因为一次委派意外获得不可控副作用。

### 2.3 版本目标

1. 建立 provider-neutral 的 Subagent 请求、状态、结果和运行器契约；
2. 通过 `delegate` 工具实现一次父 Agent → 子 Agent 的完整调用链；
3. 子 Agent 使用独立上下文、独立 Session/Run 状态和独立资源生命周期；
4. 默认提供串行、只读、最大深度 1 的安全 MVP；
5. 支持超时、预算耗尽、取消、权限拒绝和资源清理；
6. 通过父子关联事件让 CLI/TUI 能够解释委派进度；
7. 以结构化、有限长度且带证据的结果回传给父 Agent；
8. 通过离线 FakeClient 和跨层契约测试固定行为，不引入真实网络或真实凭据依赖。

## 3. 设计原则

### 3.1 委派是工具形态，执行是运行时能力

父 Agent 通过模型返回的工具调用触发子 Agent：

```text
父 Agent 请求模型
    ↓
模型产生 delegate(task, profile, budget)
    ↓
AgentTool.execute()
    ↓
SubagentCoordinator / SubagentRunner
    ↓
创建隔离的子 AgentSession
    ↓
返回 SubagentResult
    ↓
转换为 ToolResult，回填父上下文
    ↓
父 Agent 继续请求模型
```

核心 ReAct 循环只负责执行 `AgentTool`，不直接实例化 `AgentSession`，也不依赖具体的模型、工具或持久化实现。

### 3.2 生命周期模型复用，状态实例隔离

父、子 Agent 可以复用现有 `AgentSession`、`SessionRuntime`、`RunPhase`、事件和取消机制，但必须分别持有：

- `AgentContext`；
- `RunState`；
- `session_id` 和 `run_id`；
- 工具权限和资源限制；
- 取消状态和清理边界；
- 可选的持久化记录。

父 Agent 调用 `delegate` 时，父运行保持在 `tool_running` 或“委派中”，子 Agent 独立进入自己的 `starting`、`model_wait`、`tool_running` 和终态。子 Agent 结束后，父 Agent 才获得工具结果并继续推理。

### 3.3 上下文显式传递，不共享可变历史

子 Agent 只接收由父级明确构造的 `ChildContext`：

```text
ChildContext
├── 子任务描述
├── 项目级 AGENTS.md 约束
├── 选中的文件、消息或诊断事实
├── 可用工具和权限 profile
└── 输出格式、预算和完成标准
```

不默认复制父会话的完整历史、隐藏消息或所有工具输出。父 Agent 也不默认接收子 Agent 的完整 transcript，只接收经过限制的结构化结果。

### 3.4 父 Agent 是最终综合者

子 Agent 负责子任务，不负责替代父 Agent 做最终回答。父 Agent 必须能够区分：

- 子 Agent 成功完成并返回结论；
- 子 Agent 只完成了部分探索；
- 子 Agent 超时、取消或权限被拒绝；
- 子 Agent 的自然语言判断缺少可验证证据。

若子 Agent 修改了工作区，父 Agent 必须结合工作区差异和测试结果验证，不能只相信子 Agent 的文字描述。

## 5. 分阶段实施计划

### 阶段 0：v0.4 发布基线

目标是先固定上一版本的事实，避免在版本边界未完成时混入 Subagent 架构变更。

| 工作项 | 主要内容 | 验收标准 |
|---|---|---|
| 版本校准 | 更新包版本、CHANGELOG、README 和迭代文档中的版本事实 | `uv build`、版本检查和干净环境安装通过 |
| 基线记录 | 固定 `1532 passed`、OpenSpec 规格、Ruff 和发布检查证据 | CI 与本地报告能区分当前基线和历史快照 |
| 范围冻结 | 明确 v0.5 只实现串行 Subagent MVP | 非目标能力不进入本次 change |

### 阶段 1：核心契约和状态模型

目标是在不绑定具体 Session 或模型实现的前提下，定义稳定的父子委派协议。

计划内容：

- 新增 provider-neutral 的 `SubagentRequest`、`SubagentResult`、`SubagentStatus` 和 `SubagentRunner` 协议；
- 定义 `created`、`queued`、`starting`、`running`、`waiting_confirmation`、`cancelling`、`completed`、`failed`、`timed_out`、`cancelled`、`rejected` 状态；
- 将预算耗尽表达为稳定的 `reason_code`，避免为每种错误无限增加顶层状态；
- 为事件补充 `delegation_id`、`parent_run_id`、`child_run_id`、`depth` 等关联信息；
- 明确请求校验失败、权限拒绝、子运行失败和父级取消的结果映射。

验收重点：FakeRunner 可以独立测试状态转换、终态唯一性、非法状态转换和错误结果归一化；core 不导入 `session`、`tools`、`ai` 或应用配置。

### 阶段 2：串行 Subagent MVP

目标是跑通一次最小闭环：父 Agent 委派只读任务，子 Agent 独立执行并返回摘要。

计划内容：

- 在 `app/composition/subagent/` 中实现运行器、子运行工厂和 `delegate` 工具；
- 通过组合根装配子 Agent 的模型、工具、策略和资源关闭器；
- 子 Agent 直接使用独立的 `AgentSession` 或等价运行时，不调用 `SessionManager.switch()`、`fork()` 或影响当前会话的操作；
- 父 Agent 只注入 `delegate`，子 Agent 默认不注入 `delegate`，防止递归扩散；
- 子 Agent 以临时会话为默认形态，父会话只保存结构化委派结果。

验收重点：父 Agent 的 FakeClient 产生 `delegate` tool call 后，子 Agent 能完成探索，结果回填父上下文，父 Agent 能基于结果生成下一轮回答；父历史不出现子 Agent 的完整物理消息。

### 阶段 3：上下文、权限和预算治理

目标是让子 Agent 的能力边界可解释、可限制、可审计。

计划内容：

- 实现 `ChildContext` 的显式构造，区分任务、约束、事实和输出要求；
- 提供 `read_only` 和 `review` profile；
- 对工具集合进行白名单过滤；
- 默认 `max_depth=1`，限制单次父运行的子任务数、子运行轮数和墙钟时间；
- 子 Agent 的工具调用继续经过现有 `ApprovalPolicy` 和工作区边界；
- 父 Agent 取消时传播到子 Agent；
- 超时先进入取消/清理流程，无法确认清理时保留 `cleanup_uncertain` 诊断；
- 对子 Agent 的摘要、事件和结果设置有界大小。

验收重点：子 Agent 默认不能写入工作区；越过深度、时间或工具边界时不会创建未授权运行；取消、超时和失败后不存在悬挂任务、模型客户端、MCP 客户端或子进程。

### 阶段 4：结果、事件和用户可观察性

目标是让用户知道“哪个子 Agent 正在做什么、结果是否可信、失败发生在哪里”。

计划内容：

- 设计 `SubagentResult` 的摘要、发现、证据、artifact、用量和诊断字段；
- 将子 Agent 事件转发到父级事件总线，同时保留父子关联和各自序列；
- TUI 默认显示委派块、阶段、耗时、状态和摘要；
- 子 Agent 等待确认时显示明确的子任务名称、工具摘要和原因；
- 失败、超时和取消显示可操作诊断，不将失败结果渲染为成功；
- Headless 输出保留稳定的状态行和错误码，不泄露完整 prompt、密钥或无界工具输出；
- 如增加 `/subagents`，只提供运行状态、历史结果和诊断入口，不改变普通会话切换语义。

验收重点：事件乱序、子 Agent 先结束、父级取消、多个委派 ID 和迟到事件都不会覆盖错误的父会话状态；TUI 不因子 transcript 增长而重新渲染全部历史。

### 阶段 5：有限运行记录

目标是在可恢复父会话中保留委派事实，但不把临时子运行伪装成普通用户会话。

计划内容：

- 父会话持久化委派请求摘要、终态、结果摘要、关联 ID 和必要诊断；
- 子 Agent transcript 默认不进入 `/sessions` 普通列表；
- 进程重启后，未完成的子运行标记为不可恢复或 abandoned，不自动假装仍在运行；
- 已完成的父会话恢复后仍能看到子任务结果及其状态；
- 完整子 transcript、跨进程恢复和子任务搜索作为后续版本能力。

验收重点：父会话恢复不会产生重复结果、幽灵运行或错误的成功状态；旧会话缺少子任务字段时仍保持兼容。

### 阶段 6：回归和版本验收

目标是确保 Subagent 不破坏现有单 Agent 语义。

计划内容：

- 新增 core 契约测试、运行器单元测试和 FakeClient 集成测试；
- 覆盖正常完成、工具失败、模型失败、权限拒绝、超时、取消、清理不确定和父级继续回答；
- 覆盖上下文隔离、递归深度、预算、事件关联和持久化恢复；
- 增加 TUI 委派块、状态切换、迟到事件和取消交互回归；
- 更新架构文档、README、CHANGELOG 和 v0.5 迭代状态；
- 执行 Ruff、窄测试、分层测试、全量测试、OpenSpec 校验和构建检查。

## 6. Subagent 状态机

### 6.1 顶层委派状态

```text
CREATED
   ├── 校验/权限/深度失败 ──> REJECTED
   └── 接受请求 ───────────> QUEUED
                                ├── 取消 ──> CANCELLED
                                └── 获得资源 -> STARTING
                                                  ├── 启动失败 -> FAILED
                                                  ├── 启动超时 -> TIMED_OUT
                                                  ├── 取消 -> CANCELLING
                                                  └── 启动成功 -> RUNNING
                                                                    ├── 等待确认 -> WAITING_CONFIRMATION
                                                                    │                  ├── 允许 -> RUNNING
                                                                    │                  └── 中止 -> CANCELLING
                                                                    ├── 正常完成 -> COMPLETED
                                                                    ├── 执行失败 -> FAILED
                                                                    ├── 超时 -> CANCELLING -> TIMED_OUT
                                                                    └── 父级取消 -> CANCELLING -> CANCELLED
```

### 6.2 状态规则

- `completed`、`failed`、`timed_out`、`cancelled`、`rejected` 都是不可逆终态；
- 每个 `delegation_id` 只能产生一个终态结果；
- 重试创建新的 `attempt_id`，不能把已失败的运行直接改回 `running`；
- `cleanup_uncertain` 是结果诊断字段，不单独制造新的生命周期状态；
- 子 Agent 内部的 `model_wait`、`tool_running`、`awaiting_confirmation`、`compacting` 复用已有会话运行阶段；
- 父 Agent 的 `tool_running(delegate)` 与子 Agent 的状态并行存在，互不覆盖；
- 父级取消必须等待子运行进入终态或明确报告清理不确定。

## 7. 目标架构和文件职责

### 7.1 目标依赖关系

```text
CLI / TUI
    ↓
父 AgentSession
    ↓ 通过 AgentTool 调用 delegate
core/contracts                 provider-neutral 请求、结果和运行器端口
    ↑
app/composition/subagent       子 Agent 工厂、运行器、Profile 和工具适配
    ↓
独立 Child AgentSession        独立上下文、运行状态、工具集合和资源
    ↓
SubagentResult → 父 Agent ToolResult → 父 Agent 综合
```

### 7.2 规划文件

| 路径 | 职责 |
|---|---|
| `src/codeagent/core/contracts/subagents.py` | 请求、结果、状态和 `SubagentRunner` 协议 |
| `src/codeagent/core/contracts/events.py` | 父子运行关联字段和事件契约 |
| `src/codeagent/app/composition/subagent/runner.py` | 创建、执行、等待和终止子运行 |
| `src/codeagent/app/composition/subagent/factory.py` | 装配子模型、工具、策略和资源所有权 |
| `src/codeagent/app/composition/subagent/profiles.py` | 只读、审查和后续写入 Profile |
| `src/codeagent/app/composition/subagent/delegate_tool.py` | 将模型工具调用转换为子运行请求和结果 |
| `src/codeagent/session/` | 仅在需要持久化委派事实或恢复诊断时增加会话记录适配 |
| `src/codeagent/app/tui/` | 展示委派状态、嵌套进度和结果摘要 |
| `tests/core/` | 状态、协议和结果归一化测试 |
| `tests/app/`、`tests/session/` | 组合根、生命周期、持久化和取消集成测试 |
| `tests/tui/` | 委派展示、迟到事件和用户取消回归 |

`delegate` 不放入 `tools/atomic/`，因为它不是无状态文件或进程工具，而是依赖 Agent、Session 和资源生命周期的运行时能力。

---

## 8. 非目标与后续演进

以下能力不属于 v0.5 MVP 完成条件：

- 多个子 Agent 的无界并发；
- 父子共享可变上下文或共享消息历史；
- 子 Agent 自动获得完整写入、删除、提交和推送权限；
- 子 Agent 自己无限递归创建更多子 Agent；
- 跨进程、远程或分布式 Agent Worker；
- 子 Agent transcript 的完整恢复和独立会话搜索；
- 多 Agent 对同一工作区的并发写入和自动冲突合并；
- 复杂的自动任务调度、插件分发和长期记忆。

后续版本可以在 v0.5 语义稳定后增加：

1. 有界并行只读子 Agent；
2. 写入任务的独立 worktree 或沙箱；
3. 子 Agent 角色和模型选择策略；
4. 可恢复的子任务记录和重试；
5. 多 Agent 结果冲突检测与父级裁决；
6. Web/HTTP 事件消费者和远程运行器。

## 9. 风险和缓解

| 风险 | 影响 | 缓解策略 |
|---|---|---|
| 子 Agent 继承过多上下文 | 指令污染、成本升高、结果难解释 | 使用显式 `ChildContext`，默认不复制完整历史 |
| 子 Agent 继承全部工具权限 | 意外写入或危险命令 | Profile 白名单、父级策略、默认只读、最大深度 1 |
| 父级取消未传递 | 子进程和模型请求泄漏 | 统一 `cancel_and_wait`，终态前执行资源清理 |
| 超时与取消竞态 | 重复终态或错误成功 | 单一终态提交者，终态只发布一次 |
| 多个 delegate 自动并发 | 预算失控、工作区冲突 | MVP 串行；后续使用调度器和全局信号量 |
| 子 Agent 自然语言结果不可信 | 父 Agent 综合错误 | 结果携带证据、文件和测试事实；写入后由父级验证 |
| 子事件覆盖父状态 | TUI 显示错误会话或阶段 | 使用 `delegation_id`、父子 run ID 和事件作用域 |
| 子 transcript 进入父上下文 | 长会话再次膨胀 | 只回填有界摘要和结构化 metadata |
| 子运行被误显示为普通会话 | `/sessions` 语义混乱 | 临时子运行默认不进入普通 SessionManager 列表 |

## 10. 完成定义

v0.5 的 Subagent MVP 只有在以下条件同时满足时才算完成：

- 父 Agent 可以通过 `delegate` 完成一次真实的子任务委派；
- 子 Agent 拥有独立上下文、生命周期、运行 ID 和资源边界；
- 子 Agent 默认只读，递归深度和执行预算有硬限制；
- 正常完成、失败、拒绝、超时和取消都有结构化结果；
- 父级取消可以传播到子级，模型、工具、MCP 和子进程清理结果可诊断；
- TUI/CLI 能够显示委派状态，且不把失败或部分结果显示为成功；
- 父会话恢复后委派结果不重复、不丢失、不产生幽灵运行；
- 现有单 Agent、Session、工具确认、上下文压缩和 TUI 长会话测试无回归；
- 新增测试使用合适 marker，全部离线、可重复，不依赖真实 Provider 或网络；
- 通过以下质量检查：

```bash
uv run pytest -m "unit or contract" -q --strict-markers
uv run pytest -m "integration or e2e or platform or compatibility" -q --strict-markers
uv run pytest -q
uv run ruff check src tests scripts
git diff --check
openspec validate --specs
uv build
```
