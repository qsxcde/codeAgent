### 1.2 架构成熟度

当前依赖方向已经比较清晰：

```text
CLI / TUI
    ↓
app/composition        组合根：配置、模型、工具、策略和运行时装配
    ↓
session                 会话生命周期、持久化、恢复、压缩、分叉
    ↓
core                   纯内存 Agent Runtime 与 ReAct 循环
    ↓
model / tools / policy  通过端口注入的外部能力
```

核心层已经具备以下扩展接缝：

- `transform_context`：模型请求前的上下文转换；
- `before_tool_call`：工具执行前的决策；
- `after_tool_call`：工具结果修饰或终止后续请求；
- `tool_runtime`：工具执行、超时、更新事件和资源控制；
- 结构化 Agent、turn、message、tool、usage、error、aborted 事件。

因此，v0.4 不需要重新设计主循环，也不需要将 Memory、MCP、Skill 直接塞进 `core`。更合理的方向是把这些已有接缝补齐为稳定契约。

### 1.3 当前主要问题

| 问题                                               | 影响                                   | v0.4 处理                                     |
| -------------------------------------------------- | -------------------------------------- | --------------------------------------------- |

## 2. v0.4 定位与目标

### 2.1 版本定位

v0.4 的主题不是继续扩张生态，而是：

> 让已有的单 Agent ReAct 运行时稳定到可以长期使用，并为后续记忆、审计、自动化和外部消费者提供清晰的扩展边界。

### 2.2 版本目标

1. **运行可靠**：模型异常、工具失败、确认等待、超时、取消和端口热切换都有一致行为；
2. **上下文可控**：长对话在请求前可预估、可压缩、可诊断，不依赖 Provider 返回窗口错误；
3. **交互及时**：用户输入立即回显，流式输出和工具执行不阻塞输入，状态变化不造成布局跳动；
4. **会话可管理**：用户可以快速找到、恢复、整理和删除会话；
5. **扩展低耦合**：记忆、审计和遥测通过 Hook/Transformer 注入，不污染 ReAct 主循环；
6. **发布可验证**：测试、跨平台、安装、质量检查和性能报告可重复执行。

阶段 1 拆分为三个有依赖关系的变更，实施顺序固定如下：

```text
runtime-lifecycle-error-contract
    ├── 固定 RunPhase / RunState / RuntimeFailure
    ├── 固定 run_id / session_id / operation_id 事件关联
    └── 固定一次运行的唯一终态
                    ↓
runtime-cancellation-resource-safety
    ├── 接入 cancel_and_wait / wait_for_idle / aclose
    ├── 统一工具、MCP、subprocess 清理确定性
    └── 收紧 confirmation / steer / follow-up 边界
                    ↓
runtime-finalization-contract-tests
    ├── 调整消息、usage、持久化和压缩的事务式收尾
    └── 固化 Runtime 契约测试矩阵
```

阶段 1 的实现边界：

- `core` 只负责纯内存 ReAct、工具执行事实和 core 事件，不引入持久化、确认队列或 UI 生命周期。
- `session/runtime` 负责运行状态、取消协调、错误分类、确认和最终收尾。
- `SessionManager` 和组合根负责等待运行结束后再切换配置、释放会话或关闭共享资源。
- 记忆、MCP 业务编排、Skill 选择、上下文治理和 TUI 视觉改造不作为本阶段的实现内容；MCP/subprocess 的资源关闭协议属于本阶段的可靠性范围。

阶段 2 的第一个变更 `context-budget-contract` 已完成以下基线：

- `core` 提供 provider 无关的预算值对象和纯估算器，区分 system prompt、工具定义、普通历史和工具结果；
- `ChatModelPort` 按真实请求组成生成预算快照，并保留模型目录窗口、输出预留及 fallback/uncertain 来源；
- `session` 分离最近一次请求 estimate、provider actual usage 和成功提交后的 committed usage，模型切换只影响后续请求；
- 旧式 `transform_context` 继续可用，预算感知上下文扩展只生成临时模型视图，不修改 JSONL 历史；
- 本变更不包含 V4-12 请求前阻断、V4-13 自动压缩策略、V4-14 工具结果治理和 V4-16 TUI/CLI 展示，这些仍按后续变更推进。

`context-budget-preflight` 在 V4-11 基线上补齐了请求前判定：

- `core` 提供 `safe`、`near_limit`、`over_limit` 和 `uncertain` 四态结果，以及互斥的 token/比例警戒阈值；
- 每次 ReAct 模型请求在最终临时上下文准备后重新计算并发布 `context_preflight`，不会复用上一请求结果；
- `over_limit` 与 `uncertain_budget_policy="fail"` 在 provider 调用前阻断，不触发模型、工具、网络、自动恢复或重试；
- `session` 仅保存最近一次运行期 preflight 诊断，不写入 JSONL，不改变消息、usage、压缩和父级链格式；
- 组合根将阈值与不确定窗口策略透传到 CLI/TUI、会话恢复和模型切换路径；工具结果治理仍属于 V4-14，自动压缩与其专属 TUI 反馈由 `automatic-context-compaction` 补齐。

`automatic-context-compaction` 在上述预算与 preflight 基线上补齐了自动压缩：

- `CompactionPolicyConfig` 支持 `trigger_ratio`、`target_ratio`、`trigger_headroom_tokens`、`min_recent_turns`、`enabled` 和兼容性的 `compact_budget`；触发和目标均相对于下一次请求的有效输入预算计算；
- 每轮成功提交后重新估算当前模型、system prompt、工具定义、摘要、历史、工具结果、输出预留和安全余量，不依赖 provider 是否返回本轮 usage；
- 压缩按“计划 → 摘要 → 候选预算校验 → 异步持久化”执行，只在完整 user turn 边界截断；`no_safe_boundary`、`oversized_turn`、`summary_too_large`、重复上下文和失败 cooldown 均以结构化原因返回；
- 摘要 entry 持久化成功且结果确定后才更新内存 summary/history/details；已提交轮次保持 `completed/committed`，压缩失败、取消和持久化不确定分别诊断；
- TUI 复用 `COMPACTION_STARTED`/`COMPACTION_FINISHED`，显示自动压缩阶段、触发原因、前后 token、目标预算、摘要/保留轮次和跳过/失败原因；压缩期间继续保留草稿并阻止冲突提交；
- `/compact` 仍保留为手动入口。未传 `compact_budget` 时使用比例目标；显式传入时继续作为兼容性目标覆盖。策略可由 `create_agent_session` / `create_session_manager` 的 `compaction_policy` 注入。

`tool-result-governance` 在 V4-11～V4-13 的预算基线上补齐了工具结果治理：

- 工具输出使用统一的 `ToolOutputMetadata` 记录完整性、原始/展示字节和行数、截断原因、路径/范围、退出码、耗时、stderr 摘要、变更摘要及继续读取或 artifact 引用；旧字符串结果标记为 `legacy/unknown`，不再由文本标记推断为完整成功；
- 工具级硬限制在进程采集和原子工具返回处生效，bash、read、grep/find/ls、write/edit、MCP 和 skill 使用各自的头部/尾部/列表策略；进程输出统计采用流式读取，默认不会把无界 stdout/stderr 一次性物化到内存；
- 下一次模型请求前按当前模型窗口、system prompt、工具定义、历史、输出预留和 headroom 重新计算可用空间，对多个 tool call 做确定性二次裁剪；请求预算与会话累计 usage、上一模型预算相互独立；
- 事件、tool message 和 JSONL 共享同一份结构化事实。旧 JSONL 仍可读取；无 artifact 的硬截断在恢复后标记为 `incomplete`，不会写入原始无界输出；
- TUI 以结构化快照优先渲染路径、范围、退出码、耗时、变更摘要和总量/展示量，legacy 解析仅作为兼容回退；翻页和展开只作用于本地预览，不重新执行工具，无法恢复的截断结果拒绝导出。

`context-recovery-regression` 在上述上下文治理基础上补齐了恢复回归：

- MemoryStore 与 JsonFileStore 共用确定性恢复夹具，覆盖未压缩、单次/多次压缩、摘要合并、父级链、`firstKeptEntryId`、物理 JSONL 历史和恢复后的继续对话；虚拟摘要只进入模型请求，不重复落盘或进入逻辑历史。
- 覆盖压缩会话分叉、压缩边界前分叉、恢复后模型窗口切换和自动压缩预算重建，确认摘要、保留消息、父会话、usage 与下一次请求预算保持一致。
- 覆盖结构化工具结果 metadata、旧 JSONL 缺失 metadata、无 artifact 截断结果及 TUI 大会话切换竞态；不可恢复结果显示明确状态，恢复失败仍保留当前会话可用性。

## 5. 架构约束

### 5.1 ReAct 主循环不承载业务扩展

主循环只负责：

```text
读取上下文
  → 请求模型
  → 解析 assistant 内容和 tool calls
  → 执行工具
  → 写入结果
  → 判断是否继续
```

以下能力不得通过修改循环条件直接接入：

- 长期记忆；
- MCP 发现和连接管理；
- Skill 文件加载；
- 会话 JSONL 读写；
- TUI 状态和渲染；
- Provider 选择和配置读取。

### 5.2 扩展接入方式

```text
app/composition
    ├── ModelPort
    ├── Tool / ToolRuntime
    ├── ApprovalPolicy
    ├── ContextTransformer
    └── RuntimeObserver / Hook
            ↓
core.Agent Runtime
            ↓
structured events
            ↓
session / TUI / CLI / audit / telemetry
```

Hook 首版只允许观察和受控转换：

- 观察 Hook 默认只读；
- 上下文修改必须经过显式 Transformer；
- Transformer 必须受会话、项目和大小范围限制；
- 扩展失败时遵守明确的回退、取消和回滚语义；
- 不在 v0.4 执行任意第三方插件代码。

### 5.3 兼容性原则

v0.4 的优化不能破坏：

- JSONL append-only 格式；
- 会话恢复、压缩、fork 和父级链；
- `last_activity_at` 排序语义；
- 工具调用 ID 与结果归属；
- 权限确认和拒绝策略；
- `abort / steer / followup` 语义；
- AI 层与 core 的导入边界；
- Windows、Linux、macOS 的可用性。

## 6. 非目标

以下功能不作为 v0.4 承诺：

| 功能               | 延后原因                                             |
| ------------------ | ---------------------------------------------------- |
| 自动长期记忆       | 先通过 ContextTransformer 验证作用域、隐私和删除语义 |
| 完整插件系统       | 需要独立的信任、沙箱、权限和依赖协议                 |
| 多智能体协作       | 会扩大调度、会话、工具归属和交互复杂度               |
| Web/HTTP 服务      | 当前缺少真实消费者和部署边界                         |
| Automations        | 需要后台任务、调度、通知和持久化状态                 |
| MCP 完整协议生态   | v0.3 最小协议面先保持稳定                            |
| 数据库替换 JSONL   | 没有基准证据证明必须更换权威存储                     |
| 自动模型路由       | 容易把 Provider 策略与 Runtime 耦合                  |
| 跨平台绝对性能 SLO | 先用同一 fixture 做相对回归和趋势判断                |

## 7. 完成定义(DoD)

v0.4 完成时必须满足：

1. Agent 在正常、工具异常、模型异常、确认等待、取消、超时和端口切换路径下都有稳定的结构化事件和收尾语义；
2. 失败或取消轮次不会落盘不完整消息、usage 或会话元数据；
3. 上下文预算、自动压缩和工具结果治理在模型调用前可预测，并且有用户可见诊断；
4. 用户提交后立即获得回显；TUI 在长回复、长会话和高频事件下仍可输入、滚动和取消；
5. 状态栏固定槽位、工具状态和错误状态的视觉契约有回归测试；
6. 会话支持标题、搜索、筛选、归档/删除确认和恢复诊断；
7. Hook 和 ContextTransformer 只通过协议和组合根接入，异常不会破坏主循环；
8. 工具在 Windows、Linux、macOS 上具备能力探测、超时和 fallback；
9. Provider 重试不会重复执行有副作用的工具调用；
10. `uv run pytest -q`、分层测试、OpenSpec 校验、`git diff --check`、构建安装冒烟和 GitHub CI 全部通过；
11. README、架构设计、测试文档、CHANGELOG 和本迭代文档中的状态、版本和测试基线一致。

### 7.1 推荐指标

指标用于同一环境、同一 fixture 下的相对比较，不直接作为跨机器绝对承诺：

| 指标            | 关注点                           |
| --------------- | -------------------------------- |
| submit-to-echo  | 用户提交后消息出现在 TUI 的延迟  |
| submit-to-model | 用户提交到模型请求开始的本地延迟 |
| TTFT            | 请求发出到首个模型增量的时间     |
| turn latency    | 一轮 Agent 从开始到完成的总耗时  |
| tool latency    | 工具调用从开始到结果完成的耗时   |
| render p50/p95  | TUI 帧渲染耗时和长回复下的尾延迟 |
| restore latency | 会话列表和恢复耗时               |
| peak memory     | 长会话和长输出的峰值内存         |

## 8. 风险与控制

| 风险                     | 控制措施                                                  |
| ------------------------ | --------------------------------------------------------- |
| 运行生命周期抽象过重     | 先冻结事件和错误契约，使用普通 Python 状态和行为测试      |
| 自动压缩丢失关键信息     | 保留系统约束、最近轮次、工具错误和文件变更，并提供诊断    |
| TUI 性能优化改变视觉语义 | 纯组件测试、Textual 适配测试和窄终端人工检查并行          |
| Hook 造成新的反向依赖    | core 只依赖协议，组合根负责装配，增加导入边界测试         |
| 重试重复副作用工具       | 默认不重试工具；需要幂等证明和明确策略才允许重试          |
| 外部工具平台差异         | 能力探测、参数限制、纯 Python fallback 和平台测试同时保留 |
| CI 性能门禁误报          | 使用确定性 fixture、相对基线和趋势报告，稳定后再阻断      |
| 版本范围膨胀             | 每个新生态能力单独提出 OpenSpec 变更，不隐式加入 v0.4     |
