## 1. 迭代概述

### 1.1 迭代目标

v0.3 已完成 Skills、MCP、token 用量透明、会话树 UI 与全量验收。本迭代不扩展新的产品形态，重点解决长对话、长输出、会话数量增长时的响应速度和资源使用问题：

1. **先建立可重复的性能基线**:区分模型网络、工具执行、消息归约、持久化和 TUI 渲染的耗时，避免凭感觉优化;
2. **改善 TUI 流式体验**:减少每个增量事件触发的全量历史重绘，保证长回复下仍可持续滚动和输入;
3. **降低会话层 I/O 成本**:在保持 JSONL append-only 和安全权限语义的前提下，批量写入并缓存可复用的会话元数据;
4. **控制模型请求规模**:缓存工具 schema，减少重复序列化，并在请求前执行上下文预算检查;
5. **保持小项目的可维护性**:不为了未经测量的热点引入数据库、分布式缓存或复杂并发框架。

### 1.2 当前性能热点假设

> 以下是代码审查得到的待验证假设，不是已经测得的结论。阶段 0 必须先记录基线，再决定是否调整优先级。

| 区域 | 当前实现 | 可能的成本 |
|---|---|---|
| TUI 渲染 | `Transcript._rows()` 每次渲染遍历全部 blocks;流式 AssistantBlock 持续重跑 Markdown 解析 | 长历史 × 增量事件形成重复 CPU 工作，影响帧率 |
| 会话写入 | `Session.run()` 成功后逐条调用 `append_message` | 每条消息都可能重复打开文件、加锁和执行权限收敛 |
| 会话读取 | `list()`、`load_context()`、`load_usage()` 对 JSONL 做全量扫描 | 会话文件或会话数量增长后，`/sessions`、恢复和 `/status` 变慢 |
| 模型请求构造 | `_body()` 每轮重新序列化消息并生成工具 schema | 增加本地 CPU 和请求体体积，工具多时更明显 |
| 事件与渲染 | `EventBus.emit()` 同步调用订阅者;当前渲染合并主要限于同一事件循环 tick | 高频 token 事件可能让渲染追赶模型流 |
| 检索工具 | `grep/find/ls` 以 Python 遍历和读取为主 | 大型仓库搜索耗时可能明显高于模型之外的其他工作 |

### 1.4 非目标

| 项 | 说明 |
|---|---|
| 更换 JSONL 为数据库 | 只有在基准证明单机缓存和批量写入仍不足时再重估 |
| Redis、远程缓存或常驻 daemon | 不符合当前个人项目的部署和维护边界 |
| 模型供应商或模型本身优化 | v0.4 只优化请求准备、上下文规模和连接复用，不改变 provider 语义 |
| 多智能体、Web/HTTP、插件和记忆 | 延续 v0.3 的远期范围，不与性能迭代混做 |
| 隐藏或删除历史消息 | 性能优化不能破坏会话可恢复、分叉、审计和 append-only 语义 |

### 1.5 完成定义(DoD)

1. 有可重复运行的性能基准，至少覆盖:
   - 1/10/50 轮 ReAct 会话;
   - 1k/10k/20k 字符的流式回复;
   - 100/1,000 个会话文件的列表与恢复;
   - 10/100 个工具 schema 的请求构造;
2. 基准结果记录模型输入大小、TTFT、turn 总耗时、工具耗时、落盘耗时、TUI 渲染 p50/p95 和峰值内存;
3. TUI 在固定 fixture 下不再对所有历史 block 做无效重绘，滚动点击映射和 Markdown 视觉语义保持不变;
4. JSONL 仍为权威 append-only 格式，批量写入失败时不产生半轮成功记录，缓存失效后读到最新数据;
5. 工具 schema 缓存与上下文预算不会改变工具名称、参数 schema、权限决策和模型可见语义;
6. `rg/fd` 不可用、执行失败或平台不支持时，自动回退到现有纯 Python 实现;
7. 全量离线测试、OpenSpec 校验和性能回归通过，既有 v0.3 基线 666 项测试不回退。

## 3. 性能指标与验收口径

### 3.1 指标定义

| 指标 | 定义 | 目的 |
|---|---|---|
| TTFT | 请求发出到首个 content/thinking 增量的时间 | 区分网络/模型首 token 延迟与本地处理 |
| Turn latency | `SESSION_STARTED` 到 `TURN_END` 的墙钟时间 | 观察用户感知的完整轮次 |
| Tool latency | `TOOL_CALL` 到对应全部 `TOOL_RESULT` 的时间 | 识别工具本身或并发调度瓶颈 |
| Persist latency | 成功轮次开始写入到最后一条落盘完成的时间 | 衡量 JSONL 写入和锁开销 |
| Render p50/p95 | `_flush_render` 内 model render + backend render 的耗时分位数 | 防止长回复下 TUI 卡顿 |
| Prompt size | 每轮消息、工具描述和工具结果的字符/token 估算 | 控制模型延迟和 token 成本 |
| Peak memory | 基准进程峰值 RSS 或可复现近似值 | 识别长会话和全量渲染内存增长 |

### 3.2 推荐验收目标

初版先记录基线，避免跨机器绝对阈值误导。优化后使用同一环境、同一 fixture、同一 commit 对比：

- TUI 渲染 p95 相对阶段 0 基线下降至少 30%，或在 33ms 内完成固定交互 fixture;
- 会话批量落盘的单轮持久化耗时相对基线下降至少 30%;
- `list/load_context/load_usage` 在 1,000 个会话或 10MB JSONL fixture 上不出现数量级增长;
- 工具 schema 缓存命中后，请求构造耗时和 schema 序列化次数均可被测试断言;
- 任何性能优化不得改变事件顺序、工具结果归属、权限结果、会话恢复内容和分叉语义。

## 4. 演进与设计决策

| # | 决策 | 影响任务 | 说明 |
|---|---|---|---|
| E1 | 先测量后优化 | T-65~T-67 | 所有性能热点先用离线 fixture 和真实 provider 的最小冒烟分别测量;测试耗时不等于用户运行时延迟 |
| E2 | TUI 以增量渲染为主 | T-68~T-71 | 保留纯组件与 backend 端口边界;缓存只能优化渲染，不能缓存可变会话语义 |
| E3 | JSONL 继续作为权威格式 | T-72~T-75 | 批量 append 和进程内缓存是实现优化;不改变 append-only、权限、损坏行容错和恢复协议 |
| E4 | 请求预算优先于微优化 | T-76~T-79 | 对 Agent 而言减少重复 schema、无效历史和过大工具结果通常比优化 Python 小函数更有价值 |
| E5 | 外部检索器必须可选 | T-80~T-82 | `rg/fd` 仅在基准证明有收益后接入，不能牺牲 Windows、无依赖环境和安全边界 |
| E6 | 性能门禁只做防回退 | T-83~T-84 | 个人项目不建立跨机器硬实时 SLO，先保证同一 fixture 下不回退并记录趋势 |

## 5. 风险与边界

| 风险 | 影响 | 缓解 |
|---|---|---|
| 把网络/模型延迟误判成本地代码热点 | 优化投入无收益 | 指标拆分 TTFT、请求构造、工具、持久化和渲染;FakeClient 与真实 provider 分开记录 |
| 渲染缓存显示旧内容 | TUI 内容、折叠或点击映射错误 | dirty 标记与宽度/折叠状态作为缓存键;新增流式、resize、scroll 回归 |
| 缓存读到旧会话 | `/sessions`、usage 或恢复内容过期 | 所有写入口集中失效;检查文件 mtime;跨进程变化默认回源读取 |
| 批量写入破坏 append-only | 失败轮次部分落盘或 fork 链断裂 | 在同一锁范围内写入完整批次;写入失败不更新缓存;故障 fixture 回归 |
| 上下文裁剪损失模型所需信息 | Agent 行为退化 | 仅裁剪有明确预算的工具结果;先压缩并给诊断;保留权限、错误和文件变更信息 |
| 外部 `rg/fd` 平台差异 | Windows/受限环境不可用 | 启动探测、参数白名单、失败回退纯 Python;不把外部命令作为唯一实现 |
| 性能测试本身不稳定 | CI 误报或掩盖回退 | 以离线 deterministic fixture 为主;用趋势/相对基线而非单次绝对耗时做门禁 |

## 6. 后续安排

### 6.1 v0.4 结束时应具备

- 一份可提交、可复跑的性能基线报告;
- 长回复 TUI 增量渲染与节流;
- JSONL 批量写入和会话元数据/usage/context 缓存;
- 工具 schema 缓存与请求前上下文预算;
- 工具并发和大型仓库检索的基准结论;
- 不低于 v0.3 的功能、规格、安全和可恢复性验收结果。

### 6.2 暂不承诺

- 数据库迁移;
- 后台常驻服务或远程缓存;
- 绝对毫秒级跨平台 SLO;
- 多智能体、Web/HTTP、插件和长期记忆。
